**VHDL ANSWER 2026-07-18 (oracle, `membrane.vhd:157-240`).** The Next membrane
DOES have 16 dedicated extra keys on two extra columns (bits 5/6) across all 8
rows — BUT **the hardware itself synthesises every one into the exact classic
48K compound** and ANDs it into the same 8x5 matrix bits. On port 0xFE software
sees `CS+7` when UP is pressed. **So "map arrows to Next cursor keys" is a
no-op at the level jnext emulates: the existing arrows -> CS+5/6/7/8 mapping is
already exactly hardware-correct.** The distinct raw behaviour exists only via
NR 0x68 bit 4 + NR 0xB0/0xB1 — see Task 90.

Authoritative compounds for the pending mappings (all VHDL-verified):

| ZX key | Compound | | ZX key | Compound |
|---|---|---|---|---|
| BREAK | CS + SPACE | | GRAPH | CS + 9 |
| DELETE | CS + 0 | | CAPS LOCK | CS + 2 |
| EDIT | CS + 1 | | `"` | SS + P |
| TRUE VIDEO | CS + 3 | | `;` | SS + O |
| INV VIDEO | CS + 4 | | `.` | SS + M |
| EXTEND MODE | CS + SYM SHIFT | | `,` | SS + N |

Backspace -> CS+0 is already correct in `keyboard.cpp:96`; only the host-side
scancode choices remain a UI decision (the VHDL says nothing about which PC key
should trigger which ZX key).

Do: reproduce deterministically, establish the real mechanism (do not assume
the race), fix, and add a harness-selftest row that would catch it. Treat a

## Task 90: extended-keys registers NR 0xB0 / 0xB1 / NR 0x68 bit 4 — wired at NEITHER end

Github issue #33 — https://github.com/jorgegv/jnext/issues/33 (milestone v1.0, bug).

Found 2026-07-18 while answering Task 77's keyboard question. **Dead code, no
test would notice.**

The Next exposes the 16 extra membrane keys in RAW form (UP as UP, not as
CS+7) via **NR 0xB0 / 0xB1**, once **NR 0x68 bit 4** cancels the hardware
compound synthesis. Spec: `nextreg.txt:670,952-974`; read composer
`zxnext.vhd:6203-6212`; cancel bit `zxnext.vhd:5447,1584`; synthesis
`membrane.vhd:180-240`.

jnext has the model — `Keyboard::set_extended_key()` (`keyboard.cpp:322`) and
`Keyboard::cancel_extended_entries()` (`keyboard.cpp:355`), both implemented
and VHDL-cited. But:

- **no NextREG read handler for 0xB0/0xB1** — nothing in `src/port/`
- **no caller of `set_extended_key()` anywhere** outside `keyboard.cpp`

So it is connected to neither the host input nor the register file. A guest
program cannot reach it, and nothing fails.

Work: wire host keys -> `set_extended_key()`, add the 0xB0/0xB1 read handlers
composing the byte exactly as `zxnext.vhd:6203-6212` does, honour NR 0x68 bit 4
so the compound synthesis is cancelled when set, and add unit rows per bit plus
a row proving the compound DISAPPEARS from the 8x5 matrix when bit 4 is set.
Same class as issue #32 (NR 0xB2). Filed as #33 on 2026-07-18.
