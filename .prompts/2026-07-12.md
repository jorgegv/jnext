## Task 31: compositor stencil mode ignores the ULA enable (VHDL 7130)

- Found 2026-07-12 during the Task 22b review. Pre-existing emulation bug on
  the real hardware path — nothing to do with the layer mask.
- `zxnext.vhd:7130` gates stencil on `ula_stencil_mode_2 = '1' and ula_en_2 =
  '1' and tm_en_2 = '1'`. `Renderer::composite_scanline` omits the `ula_en`
  term, so a guest that disables the ULA mid-frame (NR $68 b7) under tilemap
  stencil mode keeps the AND-branch selected and gets the NR $4A fallback
  where the VHDL requires the tile pixel.
- Reproduced empirically (throwaway test row, reverted): no layer mask,
  stencil on, tm_en on, ULA disabled → jnext emits `0xFF009200` (fallback);
  VHDL requires `0xFFDD00DD` (tile).
- Needs plumbing: `composite_scanline` has no `row`, so it cannot read
  `ula_enabled_per_line_[row]` today. That is the natural scope of the task.
- `test/00regression/nex/stencil_test.nex` (added by Task 22b) is the fixture.

## Task 39: **URGENT — NEXT UP.** Cut the test/review cycle time

Measured 2026-07-12. Machine: **12 cores, 61 GB RAM**. A triplet is ~**5 min**
(4m23s and 4m58s on the two post-merge runs); reviews ran **13–40 min**, dominated
by mutation cycles (revert → rebuild → run → restore → rebuild → run, ×2-4). The
goal is a faster loop with **no reduction in work or rigour**.

Three fixes, in payoff order:

1. **Wire ccache into the build — biggest win.** `ccache` IS installed
   (`/usr/bin/ccache`) but jnext **bypasses it**: `build/CMakeCache.txt` shows
   `CMAKE_CXX_COMPILER=/usr/bin/g++`, and `CMakeLists.txt` sets no
   `COMPILER_LAUNCHER`. (The 27% hit rate visible in `ccache -s` is some *other*
   project; jnext contributes nothing.) Every rebuild is a cold compile — and the
   review loop rebuilds the world repeatedly, which is exactly where the time goes.
   - Add `find_program(CCACHE ccache)` → `CMAKE_C_COMPILER_LAUNCHER` /
     `CMAKE_CXX_COMPILER_LAUNCHER` in `CMakeLists.txt`, guarded so a machine
     without ccache still builds.
   - Raise the cache: `ccache -M 20G` (currently **5 GiB, already 3.9 used** — it
     would thrash immediately on a project this size).
   - Keeps the `make clean` discipline affordable: a clean rebuild after reverting
     one file becomes mostly cache hits, so we keep the safety without the cost.

2. **Stop hard-forcing `JNEXT_TEST_JOBS=4`.** `regression.sh:109` already defaults
   to `nproc` (12). The 4-cap comes from the day six concurrent agents each
   launched an unbounded regression and crashed the machine twice — it is a
   **multi-agent contention** rule, never a per-run requirement. Single regression
   on 12 cores should use **8**; keep 4 only when ≥3 agents run concurrently.
   Most of the ~46 headless emulator runs then go ~2× wider.

3. **Run reviewer mutations concurrently.** They are independent by construction
   (reverting the stencil gate has nothing to do with reverting the tab order), yet
   today they run serially in one worktree. Give each its own build dir and run
   them in parallel — this is the 40-min review becoming ~15.

Do **not** touch: `make unit-test` already fans all 44 suites out in parallel
(`Makefile:141-143`) — it is not the bottleneck. And do not relax `make clean`;
fix (1) is what makes it cheap.

Verify: time a triplet before and after; report both numbers. No test may be
dropped, skipped, or made less discriminative in the name of speed.
