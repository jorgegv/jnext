### Open gaps

- **G46(b)** — supervisor execution-flow divergence (alt-ROM toggle loop, ~270 ms period; AUTOMAP-NOP-sled at PC=$000C fires once with target $1F22; supervisor's PUSH/POP stack pattern at $5BFC-$5BFE diverges from CSpect: jnext = $25 08 1F vs CSpect = $00 57 0C). RAM pre-load (sysvars/screen/slot7) made supervisor reach `eff_mmu` slot6/7=$1E/$1F (new state) but Probe 28 confirms the supervisor itself overwrites pre-loaded $5C00=$FF with $00 — initial RAM state is NOT the root cause. Branch `g46b-investigation` HEAD `2d3b714`, 13 commits off `89e18de`, main UNTOUCHED.
- **G47** — post-boot regression / dot-command surface. Blocked on G46(b) landing.
- **G59** — bypass-tbblue-fw alternative path (H-effort, can run in parallel).
- **G60** — config.ini parsing (depends on G59).

The `nmi_test` BOOT group has 6 SKIPs gated on these gaps: BOOT-LOOP-01, BOOT-LOGO-01, BOOT-DOT-01, BYPASS-CLI-01, BYPASS-FAT-01, BYPASS-INI-01.

### Next-session moves (G46(b) priority)

1. **Multi-checkpoint SP probes upstream of $5B00** to identify the FIRST place where SP/stack diverges from CSpect:
   - PC=$26BE entry (NR_$13 read trampoline)
   - PC=$3E80 entry (CALL_BANK1_INLINE wrapper)
   - PC=$5B00 entry (just before bank-flip wrapper)
   - Dump SP + 8 stack words at each.
2. **Memory-write watcher on mem[$5BFC..$5C07]**: log every PC that writes those 12 bytes. Find which supervisor instructions populate the stack pattern, compare against CSpect.
3. **Trace ALL port reads** during the first 1 ms of boot: $FE keyboard, $EB DivMMC SD-SPI, $E3 DivMMC control, $7FFD/$1FFD, $243B/$253B NextREG. Look for jnext-vs-CSpect value mismatches.
4. **Audit IM2 vsync interrupt rate** during the alt-ROM toggle loop. If jnext doesn't fire IM2 at expected rate, supervisor's `EI;HALT` waits would hang.
5. **Capture more CSpect RAM**: ask user for dumps of bank-5 high half (page 0x0B = $6000-$7FFF) and additional moments earlier than first $3D00 hit. Pre-load incrementally.
6. **CSpect side-by-side trace** (would need CSpect-side instrumentation: lua hook / debugger logging).
7. **Cleanup TEMP instrumentation** (JNEXT_G46B_PATCH/INJECT/WATCH env-vars at z80_cpu.cpp) once welcome screen reaches.

**Additional instructions: Enumeration table requirement (Pass-19+):**

Before concluding ANY finding count (including zero), your audit report MUST
include an enumeration table covering every surface in scope. Format:

| Surface (file:line) | C++ behavior summary | VHDL oracle (file:line) | Match | Notes |
|---------------------|----------------------|-------------------------|-------|-------|
| ...                 | ...                  | ...                     | ✓ / ✗ | ...   |

Each row = ONE checkable claim. Granularity:

- For port-decode subsystems: one row per `register_handler(...)` call AND one
  row per VHDL `port_*` decoder entity.
- For NR registers: one row per NR address with read AND write semantics on
  separate rows.
- For CPU/Z80N: one row per opcode (or opcode group, e.g. LDIRX-family) for
  each observable behavior (flags, MEMPTR, R-reg, contention).
- For SD/SPI/DivMMC: one row per state-machine transition AND one row per
  external port.

Rules:

1. Empty cells are forbidden. If a row has no VHDL counterpart, write
   "no VHDL backing" + classify (intentional / out-of-scope / suspicious).
2. ✗ rows are findings — promote to class-(a/b/c/d) as appropriate.
3. ✓ rows must cite a SPECIFIC VHDL line, not "see entity X." If you can't
   cite a line, the row is ✗ (you didn't actually verify, you assumed).
4. Defensive-zero conclusion REQUIRES the table to be complete (every surface
   has a row). Reviewer will count rows vs source-file enumeration and reject
   the audit if coverage looks thin.
5. The table goes at the TOP of the audit report, before per-finding details.

This is not busywork. Pass-18 reviewers caught 5 missed bugs across 3
subsystems because audits claimed coverage they hadn't done. An explicit
table forces the audit to either DO the check (and find the bug) or admit
the gap (and the reviewer fills it).
