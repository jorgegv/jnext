## Task 23: NextZXOS mid-boot visual glitch

- User observed a small visual glitch mid-boot during the 2026-07-10
  native-boot verification. Investigate and fix.
- Suspects: L2 bank-5/7 routing corner (see Task 25), splash-era
  rendering, tilemap/ULA transitions during TBBLUE.FW → NextZXOS handoff.
- 2026-07-10 (eve) REPRO PINNED (user-confirmed): garbage on frames
  255-270 (t≈5.1-5.4s emulated), while tbblue.fw prints "Loading ROM:
  enNextZX.rom...OK!" — screen covered in random colour blocks; clean
  splash at 250, cleared black at 275. Capture:
  `build/gui-release/jnext --headless --machine next --sd-card
  roms/nextzxos-1gb-fat32fix.img --rtc 2026-07-10T08:55:00
  --delayed-screenshot f.png --delayed-screenshot-frames 260
  --delayed-automatic-exit 9`. Deterministic (single-frame precision).
- 2026-07-10 (eve) ORACLE ANSWER (user, real hardware): that boot phase
  shows ONLY white text on black — the colour garbage is a jnext bug.
- ROOT CAUSE (code-confirmed, = Task 25 bullet 2): jnext models bank 5
  as physical SRAM pages 0x0A/0x0B (`Mmu::to_sram_page` bypass,
  mmu.h:1146-1150) and the ULA reads those same ram_ pages
  (ula.cpp:56-75). On real HW bank 5 is a dedicated dual-port VRAM
  (zxnext.vhd:2961-2962) — separate silicon from external SRAM pages
  0x0A/0x0B. During "Loading ROM: enNextZX.rom" tbblue.fw streams data
  through the config-mode NR $04 window, which legally reaches EVERY
  SRAM page incl. 0x0A/0x0B; on real HW those writes are invisible
  (plain SRAM), in jnext they paint the visible screen → garbage on
  frames 255-270. The white loading text stays readable because it's a
  legit CPU bank-5 write.
- FIX = Task 25 dedicated-BRAM treatment for bank 5 (16K `bank5_vram_`
  buffer analogous to `bank7_bram_`, ULA/tilemap/L2 wiring, free SRAM
  pages 0x0A/0x0B as plain SRAM) + discriminative test + regression
  (the boot-nextzxos tests won't catch it — shots at 400/450 are past
  the glitch window; consider a frame-260 screenshot test after the fix).
- 2026-07-10 (night): FIXED on branch task25-bank5-vram (968914c3, with
  the Task 25 bank-5 work). Frame-260 screenshot now clean white-on-black
  — and reveals the previously-buried "Loading Multiface ROM:
  enNextMF.rom...OK!" line (NR $04=$05 = the MF bank was the writer).
- 2026-07-10 (night): review APPROVE (2 rounds: APPROVE-WITH-NITS →
  follow-ups 242843ad → APPROVE). Merged to main. New regression test
  `boot-nextzxos-splash` (frame 260) locks the fix. DONE pending user
  confirmation.

## Task 26: P3 + P5 SPI/NR03 conformance batch

- From the 2026-07 boot-branch review; non-boot-blocking VHDL conformance
  ("works by luck" gaps with our SD image):
  - SPI Ncr: exactly 2 idle bytes ($FF) before every R1 response (ours
    sends 1; fixed-count firmware readers can mis-latch).
  - CMD58 reply must not contain $FF payload bytes (tbblue.fw's reader
    skips $FF as idle and misaligns).
  - Real CRC-16/CCITT on data blocks (ours sends dummy $00s).
  - P3: cold-boot NR $03 machine-type default should be VHDL "011" (+3),
    not Pentagon-family (masked today by NextZXOS's explicit commit).
  - (moved from Task 25 triage, 2026-07-10) Multiface ROM/RAM should be
    backed by external SRAM pages 0x0A/0x0B (VHDL zxnext.vhd:3029-3036
    hard-wires the MF window there; tbblue.fw loads enNextMf.rom to that
    bank via NR $04=$05). jnext uses private buffers — pre-existing Wave 1
    design, unblocked by the Task 25 bank-5 un-aliasing. Mirror the
    DivMMC `set_ram_backing(ram_.page_ptr(16))` precedent, Next-only;
    mind MF save_state and standalone machines (real standalone MF had
    its own RAM chip).
- Each item with a discriminative unit test.
- 2026-07-11: DONE. All 5 items confirmed real gaps (not already
  conformant), each with a discriminative test that fails pre-fix:
  (1) SPI Ncr 1→2 idle $FF before R1 [TASK26-NCR-01]; (2) CMD58 OCR
  voltage byte 0xFF→0x7F, no $FF payload [TASK26-OCR-01]; (3) real
  data-block CRC-16 — implemented the SD init-0x0000 (XMODEM) variant
  per SD Phys §4.5, NOT the task text's CCITT-FALSE (documented; reviewer
  confirmed) [TASK26-CRC-00/01]; (4) NR $03 cold-boot machine-type Next
  0x04→0x03 = VHDL "011", read-back-only, no MMU-routing change
  [MT-DEF-01/02]; (5) Multiface ROM/RAM backed by external SRAM pages
  0x0A/0x0B on Next (VHDL zxnext.vhd:3029-3036), standalone keeps private
  buffers; save_state consistent [MF-SRAM-01..04]. Side effect: correct
  SD latching makes NextZXOS boot reach the splash ~8 frames earlier, so
  boot-nextzxos-splash capture moved 260→252 — reference PNG byte-identical
  (NOT regenerated; reviewer independently confirmed 248-256 stable window).
  Independently reviewed APPROVE. Merged to main.

## Task 30: make executable fully static

- Ensure the compiled binary depends on as little libraries as possible at LD runtime - ideally none.
- 2026-07-11: WONT (user decision after feasibility review). Truly
  full-static / zero-dep is not achievable for this binary on Linux:
  (1) it's a Qt GUI, so the display/GL stack (libGL/libX11/GPU driver +
  Qt's dlopen'd xcb platform plugin) is host-provided and loaded
  dynamically — a windowed app is never zero-dep; (2) static glibc
  breaks NSS/DNS, which would break the Task 27 libcurl download
  (getaddrinfo); (3) static Qt6 needs a from-source static Qt build +
  LGPL static-link compliance + plugin-import wiring. Realistic
  alternatives if portability is ever wanted: AppImage (bundle all libs
  into one self-contained file — recommended), static-link only the leaf
  libs (curl/openssl/zlib/SDL), or a musl/Alpine fully-static rebuild of
  the whole stack. All deferred; task discarded for now.
