### GH issue #33: extended-keys NR 0xB0 / 0xB1 / NR 0x68 bit 4 — wired at NEITHER end

Github issue **#33** (milestone v1.0, bug).

Do it together with issue #32

`Keyboard::set_extended_key()` (`keyboard.cpp:322`) and
`cancel_extended_entries()` (`:355`) are implemented and VHDL-cited, but there
is **no NextREG read handler for 0xB0/0xB1** and **no caller of
`set_extended_key()`** anywhere. Dead code; no test notices.

**The acceptance criterion that matters**: with NR 0x68 bit 4 SET, the CS+digit
compound must **DISAPPEAR** from the 8x5 matrix while NR 0xB0 reads the raw
key. Without that row, an implementation could pass 16 green bit-tests and
still have shipped nothing.

**UPDATE 2026-07-19 — issue #32 DONE (merged v0.98.53); #33 still open.**

Both issue texts were STALE and have been corrected on GitHub. The read
handlers for 0xB0/0xB1/0xB2 **already existed** (added 2026-04-21); #32's
claim that `JBIT_X/Y/Z` existed was also wrong (only `JBIT_MODE` did).

#32 root cause: NR 0xB2 was sourced from `Md6ConnectorX2`, which **nothing on
the host input path feeds** — `set_raw_left/right()` has no caller, and its
6-button detect needs the physical select-pulse handshake (U+D together at FSM
phase 1000) a host gamepad cannot perform. Correct composer, unreachable.
Fixed by sourcing `Joystick`, whose 12-bit vectors ARE jnext's
`i_JOY_LEFT`/`i_JOY_RIGHT` — the same field the port 0x1F/0x37 composers read,
mirroring `zxnext.vhd:6214-6215` + `:3470-3494` sharing one signal.
`Md6ConnectorX2` stays a reference model, now documented as on no live path.
Host bindings added for the dead latch bits (shoulders -> X/Z, raw 5/6/7 ->
X/Y/Z), spare non-face controls only. 20 rows NRB2-01..20; `input_test`
288 -> 308.

**Process finding (cost two REJECTs):** both rejections were sparse coverage on
code just written, never wrong behaviour. An assertion that ORs several stimuli
together **cannot detect a transposition among them** — NRB2-16 pressed both
shoulders at once and could not tell LEFTSHOULDER->X/RIGHTSHOULDER->Z from its
own swap. Mutating "the thing you were thinking about" is not enough: enumerate
every behaviour the change introduces and mutate each in isolation.

**#33 remains** and is NOT a quick fix. Its four real gaps (issue text now
rewritten to match):
1. no caller of `set_extended_key()` — `ex_matrix_` always 0, fold is dead code;
2. NR 0x68 bit 4 not honoured (write handler says "not wired here");
3. raw readback and cancellable fold are CONFLATED. VHDL keeps them separate:
   `o_extended_keys` (`membrane.vhd:253`) feeds NR 0xB0/0xB1 from the raw
   columns, immune to cancel; only `matrix_state_ex` is cleared
   (`membrane.vhd:183-186`). jnext uses one `ex_matrix_` and
   `cancel_extended_entries()` zeroes it — and **KBDHYS-03 asserts that
   zeroing**, i.e. encodes the wrong behaviour and must be reworked;
4. the fold omits CS/SYM shift synthesis (`membrane.vhd:236`/`:240`), so
   routing arrows through it would yield a bare `7` instead of `CS+7`.

**Groundwork done:** the complete fold mapping is derived from the per-index
case block (`membrane.vhd:193-226`) + the ex-register bit map (`:159-175`), and
it reproduces jnext's existing compounds EXACTLY — CS driven by all twelve
non-punctuation extended keys, SYM by EXTEND + `"` `;` `.` `,`, EXTEND driving
both (= CS+SS). So the refactor is behaviour-preserving for the default
(cancel-clear) case. That was the main risk and it is resolved.

### Task 93: lean-build link rot — ENABLE_DEBUGGER=OFF breaks the link (NEW 2026-07-19)

Found while preparing the SDL-only experiment for issue #9: `ENABLE_QT_UI`
defaults OFF, so `make release` IS the SDL-only frontend and builds fine —
but `-DENABLE_DEBUGGER=OFF` on top fails to link (`SzxSaver::save(Emulator&)`
undefined from `headless_app.cpp`): the debugger link chain is what
accidentally pulls `jnext_core` into the right static-link order. Likely a
missing `target_link_libraries` edge on `jnext_platform`. Fix + consider a CI
leg that builds the lean combo so it cannot rot again. Motivation: issue-#9
capacity-edge machines and the future ARM64/Raspberry-Pi build both want
QT_UI=OFF + DEBUGGER=OFF.

**DONE 2026-07-19 — merged v0.98.56.** The task described one missing edge;
probing ALL FOUR `ENABLE_QT_UI` x `ENABLE_DEBUGGER` combinations found a second
broken one, `QT_UI=ON + DEBUGGER=OFF`, failing on different symbols
(`Dac::reset`, `Layer2::log_bank_change`, and 7 more) — so it was never one
edge.

**Root cause:** `jnext_core` declared only input/peripheral/debug/profiler while
`emulator.cpp` holds `Z80Cpu`, `Mmu`, `PortDispatch`, `NextReg` and `Dac` as
direct members; and `jnext_platform` never declared `jnext_core` although
`headless_app.cpp` calls the savers. CMake derives static-link ORDER from the
declared graph, so an undeclared library could be ordered before its user and
the references went unresolved. It linked at all only because `jnext_debugger`'s
own dependencies perturbed the order into a working one — which is why turning
the debugger off broke it and why the failing symbols moved between combos.

**Guard:** `make build-matrix` (`test/build-matrix.sh`) builds all four combos,
reports every failure and exits non-zero; CI step added after `gui-release`
(ccache warm, ~4 min). Proven discriminative by reverting each edge in
isolation. Deliberately NOT in `test/00regression`: link rot exists only at
build time, the screenshot suite runs the binary, so four builds there would
cost minutes for zero detection power.

### GH issue #37: bug: mouse cannot be used

Github issue **#37** (milestone v1.0, bug). Branch `task96-mouse-grab` @
`ff3fbf81` — code complete, full gate green, BOTH frontends owner-verified,
independent review in flight.

**Root cause (two defects + an inconsistency).** (1) The host pointer was
**never captured** in either frontend — no `SDL_SetRelativeMouseMode`, no
`grabMouse()`, no warping anywhere in `src/`; only the cursor was hidden. A
Kempston mouse is RELATIVE, so with no capture the pointer hits the window edge
and the guest pointer stops dead. (2) Qt derived motion from the pointer's
**absolute** position inside the widget mapped onto a fixed 320x256 grid
(`main_window.cpp` `mouseMoveEvent`), so a full window traverse yielded at most
320 units of travel and the guest pointer was anchored to wherever the host
pointer entered — exactly the reported symptom. (3) The two frontends
disagreed: SDL already forwarded raw relative deltas, Qt did not.

**Fix.** Both frontends capture — click the viewport (or Input > Capture Mouse
in Qt) to take the pointer, **Ctrl+Alt** to release, nothing forwarded while
uncaptured. Qt pins the pointer to the viewport centre and forwards the delta
from it; SDL uses relative mode, which does the equivalent natively. Qt also
puts the release combo in the window title (the status message times out) and
no longer hides the cursor while uncaptured.

**Owner findings during live verification:**
- `Ctrl+M` was REMOVED as the capture shortcut: Ctrl maps to Caps Shift, so
  `Ctrl+M` IS `Caps+M`, a real ZX sequence the guest must receive. By the same
  argument **no** plain `Ctrl+<key>` may be used — capture is click-or-menu.
- Capturing from the menu threw the guest pointer across the screen while
  click-capture looked fine. Real bug: a motion event queued at the pre-warp
  position is delivered after the warp and read as one huge delta; clicking
  captures near the pointer so the delta was small. First post-capture delta is
  now discarded, and the warp echo is recognised by position rather than a
  timing-sensitive flag.
- The guest pointer staying put on re-capture is CORRECT (relative device, no
  notion of host position) — logged so it is not "fixed" later.
- Wayland worry did NOT materialise: `QCursor::setPos()` works on the owner's
  compositor.

**Coverage.** Motion policy extracted to pure `src/platform/pointer_capture.h`
(frontend handlers are reachable by no test — the Task 91 class; same reason
`render_policy.h` / `frame_deadline.h` are pure), covered by
`pointer_capture_test` (11 rows, 6/6 mutations killed). Suites 58 -> 59; the
suite pin was hand-counted, not incremented.

**Gate:** unit 59/59 suites, FUSE 1356/1356, regression 96/0/0, dashboard
regenerated.

Original report:

THere appears to be a scale problem between mouse movement inside the window and ourside it, and the mouse position in the QT/SDL window does not translate correctly to the internal ZX coordinates. So the mouse can move only in a small region of the ZX screen, and also depends on the position the real host pointer enters the emulator window. This makes mouse unusable inside the emulator.

### GH issue #40: Preferences "Apply" restarts the emulator — DONE (merged v0.98.57)

Github issue **#40** (milestone v1.0, bug). Branch `issue40-prefs-apply`,
merged to main as `a7970112`, bumped to **v0.98.57**. Two review rounds
(REJECT → fixes → APPROVE).

**Both defects confirmed in code before fixing** (unlike #32/#33, the issue text
was accurate). (1) `apply_preferences()` called `on_machine_type()`
unconditionally on every Apply, so changing only a joypad source rebooted the
machine — even though the next lines already live-applied that source. (2)
`on_machine_type()` did only `emulator_->init(cfg)`, a third incomplete variant
of the cold boot, leaving stale subsystem state and an unwired gamepad host.

the window, re-wire + re-enumerate the gamepad host, clear pending countdowns,

four optional `ColdBootHooks` std::function hooks. Ownership deliberately did
NOT go to `QtApp` (the SDL-only build has none). `MainWindow` requests reboots
via a new `RebootCallback`, shaped like the existing `LoadFileCallback`.
Apply now confirms before a machine-type restart and applies every other
setting live in all outcomes; the Machine menu restarts silently (selecting a
machine IS the explicit request) and no-ops when the type is unchanged.

**Two pre-existing SDL bugs fixed incidentally** by adopting the canonical
order: SDL carried the *startup config's* joystick sources, so any live Input
menu change was reverted by every boot; and it never cleared
`inject_countdown_`, so a pending `--inject` survived a reboot.

### FINDING 2026-07-20: rewind silently records nothing when a file is loaded

Found while writing the user-guide debugger chapter; **reproduced and
root-caused, NOT fixed, no issue filed yet** (owner asleep; GitHub writes need
confirmation).

**Symptom.** With `--rewind-buffer-size N` AND `--load <file>`, every frame
snapshot is dropped:

```
[emulator] [info]  Rewind buffer: 300 frames x 2286757 bytes = 669948 KB
[emulator] [error] save_state: buffer overflow - snapshot needs 2286760 bytes
                   but the buffer is smaller; snapshot is truncated and NOT usable
[emulator] [error] rewind: snapshot size mismatch (wrote 2286760 bytes,
                   slot is 2286757) - snapshot dropped
```

Three bytes short. Rewind appears enabled, the buffer is allocated, and the
feature records **nothing**. The process still **exits 0** - it fails silently.

**Root cause.** `Emulator::init()` sizes the rewind slot from a dry-run
`save_state()` measurement (`src/core/emulator.cpp:5920-5926`) taken **before**
`--load` is applied. Loading a file grows the serialised state, so every
subsequent snapshot overflows the slot measured for the unloaded machine.

**Confirmed by differential run** (same command otherwise, 60 frames):
- without `--load`: 0 overflow lines
- with `--load demo/copper_demo/copper_demo.nex`: overflow

**Why it matters more than the byte count suggests.** The affected case -
"debug the program I just loaded" - is exactly what the debugger's audience
does, and rewind is one of its headline features. It is also invisible: no
non-zero exit, no test row, and the user only discovers it when a rewind does
nothing.

**Suggested fix direction (not implemented):** size the slot after the load has
been applied, or size it from a worst-case/measured-at-first-snapshot value and
grow the buffer if a later snapshot needs more. Needs a test row pinning
"snapshot fits after `--load`".
