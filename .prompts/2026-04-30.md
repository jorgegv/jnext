### Current status (2026-04-30 EOD)

### What the trace shows

Frame 250 result distribution:
- 69% pixels = `0xff000000` (black)
- L2 produces opaque pixels on 56% of display, but the dominant
  result colour IS black — meaning L2 is sampling black bytes from
  its source page across most of the display area.
- Sprites contribute 9% of display pixels (clustered rows 128-159,
  matching the demo's 96 sprites at y=112/y=128).
- TM unused (parallax doesn't enable tilemap).
- 0 pixels use the `l2_prio` branch (parallax never sets the
  per-pixel L2-priority palette bit).

That black-dominant L2 output is the single most suspicious signal
remaining.

### Next lines of investigation

#### Line 1 — L2 source-page sampling

The demo populates L2 image data at runtime via DMA-paged copies
(NEX file's L2 banks 8/9/10 are all-zero per the existing analysis).
If the DMA copy timing, the NR 0x12 (active-page) value, or the
per-scanline page-shift handling is off, L2 samples zeros for most
of the visible area.

To check:
- Capture `--compositor-trace` traces at multiple frames (e.g. 60,
  120, 250, 400) and see if the L2 black-dominance is consistent or
  varies — a per-frame change would point at runtime DMA timing;
  consistent across frames would point at static page mapping.
- Cross-check with the NEX-bank → SRAM-page audit (already verified
  byte-exact earlier in the investigation, but re-verify *at frame
  250* given today's findings). Read SRAM at the L2 source-page
  address while paused at frame 250 and compare to what L2 sampled.
- Check NR 0x12 / NR 0x13 trace for parallax — is the demo writing
  these mid-frame for double-buffering?

#### Line 2 — Phase B (decode bank-6 main loop)

The disassembly covered IM1 vector install at 0x0053 and the
per-frame loop at 0x0090. The per-frame work calls were NOT yet
traced:

`CALL 0x011E / 0x01EF / 0x0213 / 0x0269 / 0x02BF / 0x00F8 / 0x0469`

Decode each by hand (z88dk-dis treats the Z80N `NEXTREG` opcode
`ED 91 nn vv` as a 2-byte NOP — manual realignment required after
each `ED 91`). For each callee, identify which NR / port writes
the demo issues each frame, and cross-reference against the trace
at `/tmp/parallax-investigation/full-trace/` (or re-capture with
`--compositor-trace` plus a port-write log). Look for any NR or
port the demo writes that jnext mishandles.

#### Line 3 — Sprite pattern data sanity-check

The 9% sprite contribution is real but might not match what CSpect
shows. Verify sprite pattern 0 contents at frame 250 (the byte
sequence in `pattern_ram_` at offset 0x000..0x0FF) against the
demo's expected sprite graphic. If pattern bytes are wrong despite
the cap fix, the DMA-paged sprite-pattern population path itself
has a separate bug.
