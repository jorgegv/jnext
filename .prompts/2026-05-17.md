### Open gaps

- **G46(b)** — IPL **self-corrupts** RAM page 0 before reaching the SD-access code, so NextZXOS never loads. Per EOD-30i+25e ([doc/issues/nextzxos-boot/g46b-v2/EOD-30i+25e-vhdl-audit-and-spi-divergence.md](../doc/issues/nextzxos-boot/g46b-v2/EOD-30i+25e-vhdl-audit-and-spi-divergence.md) + commit `485cf0aa`):
    - The 5-flag boot combo (`JNEXT_USE_CSPECT_BOOTROM_16KB=1 + JNEXT_USE_CSPECT_BOOTROM=1 + JNEXT_DIVMMC_BEATS_BOOTROM=1 + JNEXT_FORCE_AUTOMAP_AT_BOOT=1 + JNEXT_PATCH_ROM_BANK0_WITH_IPL=1`) reaches the supervisor RST $20 dispatch 22× — first time jnext gets that far.
    - The `JNEXT_G46B_RAM0_0046_WTRAP=1` trap (commit `485cf0aa`) catches the corruption at **step 318544 with PC=$012E**: the IPL's `LD BC,$02FF; LDIR` at $012B-$012F runs a SECOND PASS that writes zeros to slot 0 starting near $0040, overwriting the `D3 E3` (OUT $E3,A) at $0046 with `00 00` (NOP NOP). The first pass at steps 34-801 was the legitimate $5800 attribute clear.
    - Downstream effect: jnext's SD-via-$E3 loop runs **1×** vs CSpect's **18,795×**. Without SD I/O, the supervisor service handler at $133E stays empty and the screen stays black.
    - **VHDL audits eliminated two suspect-fixes** this iteration: jnext's NR $03 boot-ROM-disable (zxnext.vhd:5122 unconditional) and config_mode write routing (zxnext.vhd:3046, no +0x20 shift) are both VHDL-correct. The bug is upstream of those handlers.
    - Branch `g46b-investigation-v2` HEAD `7cb12123` (= `485cf0aa` + merge of main `ddd1bf47`), NOT pushed.

### Prioritized next-session moves (G46(b) priority)

**The CSpect plugin (`tools/cspect_plugin/JnextG46bTrace.cs`) is the primary diagnostic tool — zero CPU perturbation vs DZRP BPs. Prefer it for any timing-sensitive diff.**

1. **Capture Z80 regs at PC=$012E SECOND-PASS entry** (decisive, ≈30 min).
   Extend `JNEXT_G46B_RAM0_0046_WTRAP` (or add a sibling probe) to log `BC/DE/HL/A/SP` and the cycle counter the moment PC enters $012E **for the second time** (skip the first pass at steps 34-801 which is the legitimate $5800 attribute clear). The DE value names the destination region the LDIR is supposed to clear; the HL value names the source. With those, we can tell whether the second LDIR is intentional firmware behaviour misrouted by MMU state, or a stale/garbage register state from a divergent control-flow path.

2. **CSpect plugin: capture the equivalent moment on CSpect.** Extend `JnextG46bTrace.cs` with a `Memory_EXE` hook at PC=$012E that:
   (a) records visit count (filter to the 2nd+ pass),
   (b) dumps `BC/DE/HL/A/SP` via `GetRegs()`,
   (c) peeks the byte at slot 0 offset $0046 to see whether CSpect's RAM page 0 already has zeros or still has `D3 E3` at that moment,
   (d) reads `NR $50` (slot-0 mapping) to see which physical page CSpect has mapped into slot 0.
   Diff against jnext's (1). If CSpect never re-enters $012E, jnext's control-flow diverged earlier and the LDIR is spurious. If CSpect DOES re-enter $012E but doesn't self-corrupt, the difference is the destination address (DE) or the slot-0 physical mapping.

3. **Audit jnext's slot-0 MMU state at step ≈318k.** Add a probe that logs `nr_04`, `nr_50`, and the effective slot-0 physical page at every config_mode write between the first LDIR pass (steps 34-801) and the second pass (step 318544). The expectation per VHDL is that slot 0 maps to the same physical bank in both emulators throughout the IPL. Any jnext-only remap between those windows would explain the corruption: the second LDIR writes to what jnext thinks is "scratch RAM" but is in fact the IPL's own code page.

4. **Backup hypothesis — destination register is garbage from divergent control flow.** If (1) shows DE pointing somewhere other than a valid clear region (e.g. `$0040`), the bug isn't in the MMU mapping — it's that the IPL took a different path *to* $012E with stale register state. Bisect by adding a per-PC ring-buffer (16 entries) around the second-pass entry and diff against the equivalent CSpect ring via the plugin.

5. **Cleanup TEMP instrumentation** (`JNEXT_G46B_*` env-vars at `z80_cpu.cpp` and `mmu.h`) once the welcome screen renders.
