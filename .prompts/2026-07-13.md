## Task 31: compositor stencil mode ignores the ULA enable (VHDL 7130)

**The most valuable thing here: a real emulation bug, already reproduced, with a
fixture in place.**

- Found 2026-07-12 during the Task 22b review. Pre-existing, on the real hardware
  path — nothing to do with the layer mask.
- `zxnext.vhd:7130` gates stencil on `ula_stencil_mode_2 = '1' and ula_en_2 = '1'
  and tm_en_2 = '1'`. `Renderer::composite_scanline` omits the `ula_en` term, so a
  guest that disables the ULA mid-frame (NR $68 b7) under tilemap stencil mode keeps
  the AND-branch selected and gets the NR $4A fallback where the VHDL requires the
  tile pixel.
- Reproduced empirically (throwaway test row, reverted): no layer mask, stencil on,
  tm_en on, ULA disabled → jnext emits `0xFF009200` (fallback); VHDL requires
  `0xFFDD00DD` (tile).
- Needs plumbing: `composite_scanline` has no `row`, so it cannot read
  `ula_enabled_per_line_[row]` today. That is the natural scope of the task.
- `test/00regression/nex/stencil_test.nex` is the fixture.

## Task 13b: Standard snapshot formats — DONE (reopened once, redone)

Delivered: **`.z80` loader** (v1/v2/v3, 48K/128K — closes G34) and **`.szx` / `.nex` savers**
(closes G35). Un-skipped BOOT-Z80-01..05 and BOOT-SNAPSAVE-02/03.

**The `.szx` saver was built wrong twice before it was built right, and that sequence is the
point of this entry:**

1. First cut wrote **112 RAM banks**. Every round-trip test passed — because they went through
   *jnext's own* `SzxLoader`, which has no page-number upper bound. Saver and loader shared the
   same blind spot, so the suite was self-consistent and wrong.
2. A reviewer loaded the output in **real FUSE**: `szx.c:read_ramp_chunk: unknown page number
   64`. libspectrum hard-rejects any RAM page > 63, so **every `.szx` file jnext could produce
   was unreadable by the reference implementation.**
3. The first fix — clamp to 64 banks — was the **wrong shape**, and the user rejected it:
   `.szx` is a *classic-Spectrum interchange format*, not a Next container.

**What shipped (2026-07-13):** `.szx` saves **only the machine's real pages** — `{5,2,0}` for
48K, `{0..7}` for 128K/+2A/+3, per libspectrum's own `write_ram_pages()` (szx.c:3330-3342) —
with the correct `chMachineId` (48K=1, 128K=2, +2A=4, +3=5). On **Next it REFUSES to save**
rather than lying in the header (it previously claimed to be a +3): no file, non-zero exit, and
a message pointing at `.nex`. The 64-bank clamp, the truncation plumbing and the always-firing
GUI truncation warning are gone.

Interop is proven **independently of jnext's own loader**, twice: real `libspectrum_snap_read()`
accepts all three machine types, and a reviewer's from-scratch SZX parser decoded the screen page
and matched jnext's framebuffer **pixel-for-pixel** — which is what rules out the nastier failure
mode, a file FUSE *accepts* but restores with scrambled memory.

**Standing rule this produced:** a file-format saver must be validated against a **foreign
reader**. Round-tripping through our own loader proves nothing.

Still open, and the real answer for Next state: **Task 13a** (Next-specific snapshot schema,
PARKED). `.szx` structurally cannot carry it.

## Task 38: `make clean` silently reconfigures build/ with ENABLE_QT_UI=OFF

- Found 2026-07-12 during Task 36 (cost the author two failed capture runs).
- `ENABLE_QT_UI` defaults to **OFF** (`CMakeLists.txt:32`), and `unit-test-build`
  reconfigures `build/` passing only the compilers — **not** `-DENABLE_QT_UI=ON`
  (`Makefile`). `make clean` → `unit-test-clean` → `rm -rf build`. So after any
  triplet run, the canonical `./build/jnext` is the **SDL** binary with no Qt main
  window — even though CLAUDE.md's standing rule says always build with
  `-DENABLE_QT_UI=ON -DENABLE_DEBUGGER=ON`.
- Consequence: anyone doing GUI verification against `./build/jnext` after a test run
  finds no window at all, and it looks like their change broke the UI.
- Fix: have `unit-test-build` configure with the flags the project's own rule
  mandates, or make the mismatch loud (refuse to run / warn when `build/` was
  configured without them).
- Silver lining, worth keeping: this accident proves the `ENABLE_QT_UI=OFF` build
  **compiles and runs**, which is the empirical half of Task 26's clause 3.

## Task 41: debugger audio panel decodes a 2-bit PSG stereo field that does not exist

- Found 2026-07-12 by the Task 40 reviewer. Pre-existing.
- `src/debugger/audio_panel.cpp:176-178` reads `(reg08 >> 4) & 0x03` and indexes
  `{"ABC","ACB","BAC","BCA","CAB","CBA"}`.
- VHDL `zxnext.vhd:5177-5178` + `:5906` + `:6399`: NR 0x08 **bit 5** is
  `nr_08_psg_stereo_mode`, a **one-bit** field (0 = ABC, 1 = ACB). **Bit 4** is
  `nr_08_internal_speaker_en` — a different signal entirely.
- Consequences: toggling the internal speaker changes the displayed stereo mode; ACB
  renders as "BAC"; and "BAC"/"BCA"/"CAB"/"CBA" are not ZX Next stereo modes at all.
  The panel is inventing a field.
- Fix: `(reg08 >> 5) & 1` over `{"ABC","ACB"}`. Needs a test — `audio_panel` has **no
  test coverage** today, which is exactly why this survived.

## Task 43: two per-line NR 0x68 snapshots are dead code (NEW — found 2026-07-13)

- Found by the Task 31 **reviewer**, confirmed by grep. Pre-existing, out of scope there.
- `src/video/renderer.h:327-355` declares `stencil_mode_per_line_` and
  `blend_mode_per_line_` with full snapshot/init/accessor methods — and **nothing ever
  calls them**. Zero call sites for `snapshot_stencil_mode_for_line`,
  `init_stencil_mode_per_line`, `snapshot_blend_mode_for_line`,
  `init_blend_mode_per_line`.
- Consequence: `composite_scanline` still reads the **live** `stencil_mode_` /
  `blend_mode_` registers, so a mid-frame Copper MOVE to NR 0x68 **bit 0** (stencil) or

  deferred to the next — unlike `ula_en` (fixed in Task 31), NR 0x4A and NR 0x14, which
  are all correctly per-line snapshotted.
- The infrastructure is already written; it just needs wiring from `emulator.cpp` next to
  the existing `ula_enabled_per_line_` snapshot call, plus discriminative rows.

## Task 46: Layer 2 reads NR 0x14 transparency LIVE, and skip-writes (NEW — 2026-07-13)

The sixth and last instance of the per-line-deferral bug class — and the only one with a
**user-visible rendering consequence**. Found by the Task 45 author, **confirmed by the Task 45
reviewer** (both the bug and the sharper claim below).

- `src/video/layer2.cpp:373` computes its transparency gate from
  `PaletteManager::global_transparency()` — a **separate live member** (`palette.h:429`), written
  from the same NR 0x14 handler (`emulator.cpp:1061-1064`) that also calls
  `renderer_.set_transparent_rgb(v)`. Per VHDL `:7121`, `layer2_transparent` must use the same
  **deferred** `transparent_rgb_2` as ULA and Tilemap (fixed for those in Task 45).
- **Why this one actually bites:** Layer 2 **skip-writes** (`layer2.cpp:429-430`:
  `if (palette.layer2_rgb8(idx) == transp_rgb) continue;` — it never writes `dst[]`), leaving the
  pixel at the buffer's transparent sentinel. So a pixel Layer 2 wrongly decides is transparent
  (using the *live* value) is **gone** — `composite_scanline`'s now-correct check cannot recover
  it. The compositor's `(l2_px & 0xFFFFFF) == nr14_rgb` test at `renderer.cpp:518-519` can only
  fire in the narrow reverse case, and in steady state never fires at all — it is **largely dead
  code today**.
- Fix shape (author sized it, small): give `Layer2::render_scanline` a `uint8_t transparent_rgb`
  parameter, pass `transparent_rgb_for_line(row)` from `render_row`, and keep the live value in
  `render_scanline_debug`. The signature change is why it was scoped out of Task 45 —
  `video_panel.cpp` also calls it for the debugger's isolated-bank views.
- Needs a discriminative deferral row (row N keeps the old value) **and** a row proving a
  wrongly-skipped pixel is no longer lost.
