## Task 50: the contention window was displaced by 64 scanlines — DONE (merged)

**MERGED to main. Found while chasing Nirvana; it is NOT a Nirvana bug — it mis-timed every
contended 48K/128K/+3 program.**

**REJECTED on first review, and the reviewer was right:** `T50-01` was **theatre**. It probed the
top border at raw hc=160, where `hc_adj = (160 & 0xF) + 1 = 1` and `1 & 0xC == 0` — so the
HORIZONTAL phase gate returns 0 whatever vc says. The row reported "the border does not contend"
while actually measuring "this hc phase never contends", and **passed with the bug still present**.
Proven by mutating `to_ula_counters()` to identity: the other five T50 rows failed, T50-01 sailed
through. Probe moved to raw hc=120 (contends in BOTH coordinate systems), so only the vertical
border check can zero it. All six now fail under mutation. **The author had written the
mutation-test instruction into the review brief and had not run it on their own rows.**

`ContentionModel::contention_tick()` gates on `border_active_v`, transcribed correctly from
`zxula.vhd:414` (`i_vc(8) or (i_vc(7) and i_vc(6))` → "border when vc >= 192"):

```cpp
if ((hc & 0x100) != 0) return 0;               // src/memory/contention.cpp:255-258
if ((vc & 0x100) != 0) return 0;
if ((vc & 0xC0) == 0xC0) return 0;
```

The transcription is right; **the inputs are wrong.** In the VHDL, `i_hc`/`i_vc` are the ULA's
**display-relative** counters — `zxula_timing.vhd:441-452` resets `vc_ula` to 0 at `c_min_vactive`
(the first display line) and `hc_ula` at `ula_min_hactive` (`= c_min_hactive - 12`, `:423`). That
is *why* "vc >= 192 = border" is the correct test there. jnext feeds the gate the **raw frame
counters** from `derive_hc_vc()` (`src/cpu/z80_cpu.cpp`), where vc=0 is the frame start and the
display only begins at vc=64. So the window sits 64 lines too high:

- contention **is applied across the top border** (raw vc 0-63) — a real Spectrum applies none;
- contention **is not applied over the bottom 64 display lines** (raw vc 192-255) — it should be.

The two errors partially cancel over a frame, which is why no screenshot regression caught it.

**Measured against real FUSE** (headless — see the FUSE oracle recipe below) on bifrost.tap.
Same PC, same code path, INT-relative T-state of the write to `$5865`:

| | jnext before | jnext fixed | FUSE (oracle) |
|---|---|---|---|
| contention T charged since INT | 1118 | **290** | ~310 (implied) |
| INT-relative T of the write | ~20492 | **~19716** | **19684** |

**~870 T of phantom contention per frame → +32 T.** A ~96% reduction, independently re-measured
by the reviewer via gdb on the `tstates` global (FUSE cycles 19684, 19908, … +224/phase over 8
phases; jnext post-fix 19716, 19940, … — the **same** 8-phase cycle).

**The +32 T residual is a CONSTANT bias on every phase — NOT jitter.** I originally called it
"within INT-acceptance jitter"; the reviewer measured it and there is no jitter, it is a fixed
offset. See Task 52.

**Fix (implemented):** rebase raw (hc, vc) onto the ULA counters before the gate, per machine,
from `VideoTiming` (`ula_prefetch_origin_hc()`, `display_origin().vc`) — pushed into the CPU via
the new `z80_set_ula_counter_origins()`. **No hardcoded 48K constants.**

**Nine existing tests were passing BECAUSE of the bug** — this is the part worth remembering:
- `CT-INT-01`, `CT-DELAY-01`, `CT-FUSE-01/02/05` ran their timing programs from `tstates = 0`
  (raw vc 0 = **top border**) and asserted contention fires there.
- Four `cpu_z80n_im2_regressions` rows seeded `tstates = 2` with the comment *"hc=4, vc=0,
  **active raster**"*. They meant ULA coordinates and got raw ones for free.

All were corrected to express their *same intended raster position* properly, not to go green.
Beware one trap: the IntSmoke program reads every 20 T (= 40 ticks ≡ 0 mod 8), so its contention
phase is **locked** by wherever it starts — whatever bin of the VHDL wait pattern
`{6,5,4,3,2,1,0,0}` the first read lands in, every read lands in. **Do not hunt for a start offset
that produces a nonzero result** (that is the Nirvana arm-heuristic anti-pattern). The helper
anchors on the ULA counter origin `(hc_ula, vc_ula) = (0,0)` — the hardware's own window opening —
which is defensible without looking at the outcome.

**New test rows: `T50-01..06`** in `contention_test` (89 → 95, manifest updated deliberately).
They drive the **production seam** — set the FUSE T-state counter to a raster position, call the
real CPU memory callback, measure what it charges — instead of calling `contention_tick()` through
its front door with pre-cooked coordinates. That seam is what was never tested: the 68 existing
rows pass ULA-relative coords, production passed raw ones, and nothing checked the two agreed.

**Outcome:** regression **64/0/0 — ZERO reference screenshots moved**, despite this changing memory
timing for all contended software. That is the two halves of the bug (over-contending the top border,
under-contending the bottom third) cancelling over a whole frame — exactly why it survived so long.

### Task 54 update (2026-07-13 night): root cause found; residual re-measured at +11 T

The bulk of the bias WAS the wrong-period stretch table (Task 54). Post-fix, BIFROST's writes

- **Part of it may be hardware-REAL.** zxula.vhd:580-581 says the Next contends hc 3-14

  sub-octet-precision demo appears, and then start by settling the anchor question against real

## FUSE as a headless, scriptable oracle (NEW — this is a big one)

FUSE renders BIFROST correctly and **ZEsarUX does not**, so FUSE is the oracle. It can be driven
**headless and scripted**, which turns "compare screenshots by eye" into "compare T-states":

```bash
export DISPLAY=:78
Xvfb :78 -screen 0 1024x768x24 &          # X11 — xdotool/import work in here; Wayland they do NOT
printf 'break write 0x5865\ncommands 1\nprint ula:tstates\ncontinue\nend\ncontinue\n' > dbg.txt
GDK_BACKEND=x11 timeout 25s /usr/bin/fuse --machine 48 --no-sound --auto-load --traps \
    --debugger-command "$(cat dbg.txt)" --tape test/00regression/tap/bifrost.tap
```

- `--debugger-command` is **not in `--help`** — it is in `man fuse`. It is the only way to feed
  multi-line debugger commands.
- `break write ADDR` / `break ADDR` / `break port read|write P`, `commands ID … end` (auto-run on
  hit), `print EXPR`, `continue`. Numbers print in **hex**.
- **`ula:tstates` = T-states since the last interrupt** — exactly the frame of reference a
  beam-racing demo works in, and directly comparable to jnext's own INT-relative counter.
- `import -window root out.png` under Xvfb captures the screen (this is how the oracle PNG and a
  repeatable oracle generator were obtained).

This is what turned the Nirvana investigation from guesswork into measurement: same PC, same code
path, one number each side, difference = 808 T.

## Diagnostic discipline (paid for in real time)

- **A demo passing is not proof the model is correct.** Nirvana "looked right" for two rounds while
  the model was wrong. **BIFROST is the discriminating demo** — that is why all three TAPs exist.
- **Do not tune a constant until the tests go green.** The Nirvana arm heuristic and (nearly) the
  Task 50 test anchor were both this trap. *A heuristic tuned until the tests stop failing is
  indistinguishable from a bug fix, right up until someone removes the heuristic.*
- **Test the hypothesis before fixing it.** The T-state write-timestamp theory was plausible,
  self-consistent, and explained every observation — and was worth **3 pixels**. One probe
  (0.71% of writes mis-tagged) killed it in one build.
- **When a fix makes existing tests fail, ask whether they were asserting the bug.** Nine were.
- **Crop to the 256×192 display area before pixel-diffing** (jnext writes 640×512, FUSE's window
  was 1276×957); point-sample only (`-sample`, never an interpolating resize — it invents colours);
  calibrate alignment on something the feature does not touch (the plain-ULA text), never on the
  thing under test.
- Demo NEX/TAP runs take `--machine 48k|next --load FILE` and **no `--sdcard`**.
- The user's clipboard screenshots: `wl-paste --type image/png > out.png`.

## Task 54: contention stretch magnitudes had the wrong PERIOD; mux fetch instants were parity-blind (DONE — 2026-07-13 night)

The user isolated BIFROST's residual glitch precisely: attributes in char cols 16-18 rendered
exactly ONE scanline early. Two bugs, both found by measuring BIFROST's per-write beam positions
against real FUSE (`break write` + `ula:tstates`, the Task 50 oracle recipe):

1. **`pattern[hc & 7]` in `src/memory/contention.cpp` (on main since G141) indexed FUSE's
   per-T-STATE stretch table with a PIXEL-TICK counter** — repeating the 8-T-state pattern every
   4 T-states and under-charging 5 of the 6 contended phases (14 T instead of 21 T per octet).
   Correct per VHDL (zxula.vhd:582-583 + zxnext_top_issue2.vhd:1024-1140 clock-stretch
   consumption): 48K/128K `{0,0,0,6,6,5,5,4,4,3,3,2,2,1,1,0}[hc & 0xF]`, +3
   `{1,0,0,7,7,6,6,5,5,4,4,3,3,2,2,1}[hc & 0xF]`. BIFROST is a contention-LOCKED engine: FUSE
   holds its writes at ts_in_line=80 for 144 straight scanlines; jnext drifted ~2 T/line for 12
   lines and locked 22 T early, pushing cols 16-18's writes across the ULA fetch boundary.
   **This was also the root cause of Task 52's "+32 T constant bias".** Post-fix jnext locks
   wobble-free at ts_in_line=91: a constant **+11 T residual vs FUSE remains** (candidates:
   INT-acceptance timing; the 1 T FUSE-vs-VHDL contention anchor difference — "contend 3-14"
   synchronous vs "contend 4-15" combinatorial, zxula.vhd:580-581) → tracked under Task 52.
2. **`AttributeMux::hc_fetch()` was 8-12 ticks early and parity-blind.** Per zxula.vhd:271-306 +
   :368-455 the byte governing column C latches at raw hc `min_hactive + 8C` (even C) /
   `min_hactive - 4 + 8C` (odd C) — sload_0/sload_1 consume abyte00/abyte10 latched 1/5 ticks
   earlier. Round 4's `origin + col*8` and its "sload stagger has no CPU-write-race observable"
   comment were wrong.

**Result: BIFROST renders logically pixel-identical to real FUSE — 0/49152 differing pixels on
BOTH demo screens (modulo FLASH capture phase); Nirvana's bricks render yellow, matching FUSE.**
Measurement protocol, stated precisely because a raw RGB diff will NOT show 0: the two emulators
render the ZX "normal" intensity at different levels (FUSE 0xC0=192, jnext 0xDB=219 per RGB333;
both use 0xFF for bright), so compare ZX colour INDICES — either quantize both sides to the
16-colour palette, or map FUSE's 192→219 and then raw-diff. Verified both ways; also verified the
per-level channel histograms match exactly (3395 samples at normal level, 6678 at bright, per
frame, both sides) — i.e. the BRIGHT bit agrees at every pixel, ruling out same-hue
brightness-band displacement from the +11 T residual.

Test fallout, audited row by row: 10 contention rows + G12-MUX-10 had derived their expected
values from the wrong table/formula (asserting the bug); corrected with VHDL-cited derivations.
CT-WIN-07's sweep was green with both sides wrong because `contention_helpers.h`'s
`expected_wait_pattern()` MIRRORED the production table — helper removed, expected table now
INLINE literals in the row. G12-MUX-11 added (parity discriminator: one write instant lands after
col 4's fetch but before col 5's; a third probe kills parity-blind formulas). mmu_test 251→252.
Both fixes mutation-tested before review: reverting the stretch table turns 10 rows red;
reverting hc_fetch turns both G12-MUX rows red.
