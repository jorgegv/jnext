### GH issue #42: rewind silently records nothing when a program is loaded (v1.0)

**Root-caused 2026-07-20 while writing the user guide; NOT fixed.** Highest-value
open item.

- Symptom: `--rewind-buffer-size N` + `--load FILE` ⇒ every frame snapshot is
  three bytes too big, is dropped, and the process still **exits 0**. Rewind
  appears enabled and records nothing.
- Root cause: `Emulator::init()` sizes the rewind slot from a dry-run
  `save_state()` measurement (`src/core/emulator.cpp:5920-5931`) taken **before**
  `--load` is applied; loading a file grows the serialised state.
- Confirmed by differential 60-frame run: no `--load` ⇒ 0 overflow lines;
  `--load demo/copper_demo/copper_demo.nex` ⇒ overflow every frame.
- Fix direction (not implemented): size the slot after the load has been
  applied, or measure at first snapshot and grow the buffer when a later
  snapshot needs more.
- **Needs a test row pinning "a snapshot still fits after `--load`"** — the
  defect is invisible to the current suite (no non-zero exit, no row).

### Completion notes — the issue's stated cause was WRONG

Branch `issue42-rewind-size` @ fc5e1c04 (worktree `jnext-worktrees/issue42-rewind`).

- **Disproved the issue's mechanism.** Bisected the snapshot with a temporary
  per-sentinel position probe: the size is **identical with and without
  `--load`** (2286757 B at all 29 sentinels). "Sized before `--load` applies"
  does not hold.
- **Real cause**: `Ula::save_state` wrote the per-scanline port-0xFF change log
  count-prefixed and **variable-length** (3 B/entry), and
  `Keyboard::save_state` did the same for the auto-type queue (20 B/entry).
  `RewindBuffer` sizes each slot from one dry run and demands exact equality, so
  the first frame the guest writes port 0xFF is 3 B over and is dropped.
  Confirmed by instrumenting the count: with `--load` one frame has
  `port_ff_count=1` (the dropped one), without it every frame is 0.
- `--load` is a red herring — copper_demo happens to write port 0xFF once during
  init. Typing a program in by hand does it too.
- **Severity is guest-dependent**: copper_demo loses one rewind point; a program
  setting Timex mode every frame loses *every* snapshot, which is the "records
  nothing" of the title. The drop path itself is sound — nothing is corrupted.
- **Fix**: both fields serialise at full capacity (constant width);
  `Keyboard::MAX_AUTO_TYPE_KEYS = 16` enforced at `queue_auto_type()` (every
  in-tree caller queues ≤ 4). Free to change the layout because snapshots are
  in-memory only — `RewindBuffer` is the sole caller of `save_state`/`load_state`.
- **`rewind_buffer.h` already asserted the stream was fixed-width**, which is
  why this was invisible. Comment corrected to record why, so the next
  variable-length field added gets caught.
- Tests RB-SIZE-01..06; manifest pin 66 → 72. Both fields mutation-tested
  (reverting ULA kills 01/02, reverting keyboard kills 04/05/06). Also converted
  a `REQUIRE` to `CHECK` so a regression cannot destabilise the pinned row count.
- Triplet on the branch: unit **5288/5288 (63 suites)** • FUSE **1356/1356** •
  regression **96/0/0**. Original repro now clean at 60 and 400 frames.
- Independent review dispatched (not self-reviewed).

### GH issue #38: Soundrive DAC playback has a continuous background buzz (v1.0)

- Reproduces on ZEsarUX too, with interrupts disabled, 28 MHz CPU and a pure-asm
  deterministic playback loop. Unknown whether the fault is the demo, jnext's
  DAC/mixer sampling, or software-driven DAC playback in general. DAC is rarely
  used by Next software — low priority.

### Completion notes — NOT a jnext defect; closed not-planned, merged v0.98.68

- **Cause: the demo, not the emulator.** It drove channel D via port `0xDF`,
  which is the Specdrum **mono** port and writes channels A *and* D together
  (`zxnext.vhd:2661,2664` via `port_dac_mono_AD`), and it had B/D on the wrong
  sides. Net: `chA=chD=sample_a`, `chB=chC=sample_b`, so **both sides carried
  `sample_a + sample_b`** — measured L/R correlation exactly **1.000000**.
  `sample_b` is the 3rd harmonic of `sample_a` (phase step 3 vs 1 over the same
  256-entry table), and fundamental + near-equal 3rd harmonic *is* the hollow,
  reedy buzz.
- jnext decodes per `soundrive.vhd:112-113` (`pcm_L=chA+chB`, `pcm_R=chC+chD`)
  correctly throughout — which is exactly why ZEsarUX reproduced it identically.
- **Owner verified on real Next hardware**: dac_demo sounds the same there. That
  closed the one gap the investigation had flagged as unproven (it predicted
  hardware would sound identical but could not test it).
- Aliasing hypothesis was raised and **discarded on evidence**: HF/LF energy
  ratio 2.5e-5, and `advance_audio` already box-integrates the DAC level across
  each 44.1 kHz interval — the correct decimation prefilter. No DC blocker was
  added (that was a masking fix, reverted in v0.95.x — do not reintroduce).
- Review found one unreproducible number: the "h3 at −3.8 dB" claim. Independent
  re-measurement puts h3 at **roughly equal amplitude** to f0 (+0.2 dB), which is
  what the code predicts (same unscaled table). Corrected in a follow-up commit
  rather than amended (block-amend hook; new commit is the convention).
- Landed: merge `44e896ec`, design-plan §11 row marked resolved `697e0ce7`,
  bump `7b434c66` = **v0.98.68**. GitHub issue closed `NOT_PLANNED` with the
  evidence summary. Not pushed.
