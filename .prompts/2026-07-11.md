## Task 23: Fix strange sound in Cesare intro

- The Cesare intro (just after load) uses beeper music extensively, and seems to have a clicking sound overimposed with the real music.
- Investigate
- Related to github issue #7
- **FIXED (v0.96.0).** Not merely *related* to issue #7 — the clicking **is** issue
  #7. Two distinct bugs were spoiling the beeper music:
- **(1) Audio-device underruns = issue #7 "constant noise".** Audio is synthesised
  on the *emulated* clock but the frontends paced on the wall clock. A 48K frame is
  69888 T = 50.08 Hz against the 20 ms tick, so jnext fed the sound card 44030
  samples per real second while it consumed 44100. The queue drained to empty in
  ~20 s and SDL spliced **zeros** into a live waveform, 2-3x/second, forever.
  (128K/Next = 49.36 Hz *over*-produces instead, and the old code drained the mixer
  ring then discarded it — same cause, opposite sign.) On a CPU-tight host — issue
  #7's reporter — the deficit is far larger and the click train becomes a continuous
  buzz, audible even on a **silent idle machine**, because the pre-#7 mixer rested
  at DC +2048 so every injected zero stepped 2048 -> 0 -> 2048. Measured: 100 such
  steps in 35 s of idle. Fixed by pacing emulation on the audio device's clock
  (`src/platform/audio_pacing.h`).
- **The v0.95.x DC blocker never fixed issue #7 — it masked it**, by pulling idle
  output to 0 so the injected zeros became a no-op. It also sagged every beeper
  plateau by a median 8.6%. `audio_mixer.vhd` has no AC-coupling stage. Reverted.
- **(2) Mixer point-sampling -> aliasing** (the "higher pitch over the tune", found
  once the clicking was gone). The mixer was read once per output sample (~79
  T-states apart); a 1-bit beeper engine toggles far faster, so most toggles were
  never observed and their energy folded down as an inharmonic tone over the melody.
  It now *integrates* over each sample interval, as FUSE does.
- Verified: Cesare 45.9 s -> **0 underruns** (was 76 in 41 s); energy >6 kHz
  **6.2% -> 1.8%**. New `audio-underrun-func` regression test reports 24-25
  underruns on pre-fix main and 0 after. Three independent reviews.
- Two speculative fixes were built, measured as no-ops and deleted: cycle-exact
  speaker-edge placement (every beeper write lands at exactly T-state 8 of its OUT,
  so it was a uniform shift) and an 8x-oversampled 255-tap decimator (1.81% ->
  1.82%). The residual HF is inherent to the 1-bit signal, not aliasing; FUSE
  differs only because it low-passes the beeper, which is a tone choice.

## Task 24: remove constant logging CPU changes

- There are several demos and programs that change the CPU speed frequently, and the logs show this as [info] level.
- Let's review the general philosophy fo debug messages an iterate over it, decide a general policy, and implement it reviewing all log lines and adjusting the log level if needed.
- **DONE.** Policy documented at the top of `src/core/log.h` — read it before adding
  a log line. The rule that decides almost every case:
  **`info` is for what the USER did; `debug` is for what the GUEST did.**
  (`error` = the operation failed; `warn` = emulation continues but degraded;
  `trace` = per-instruction firehose.) Plus two mechanical rules: nothing above
  `debug` in a per-frame/per-port-write path, and **a guest state change logs only
  when the value ACTUALLY CHANGES**.
- Applied to all 335 log calls. NR 0x07 CPU speed: `info` → `debug` **and**
  change-gated (it logged on every *write*, not every *change* — that was the
  spam). A default `--machine next` boot went **26 → 15** lines.
- New: a bare level in `--log-level` sets every subsystem (`warn`), mixable with
  per-subsystem tokens (`warn,emulator=debug`), applied left to right.
- Bugs found along the way: `--log-level ctc=debug` / `i2c` / `multiface` **never
  worked** (loggers created lazily, never registered in `Log::init()`, so
  `set_level` failed silently — demoting their lines to debug would have made them
  unreachable); an unrecognised level string silently **mutes** a subsystem
  (`from_str` maps anything unknown to `off`, so `video=warnn` kills video logging
  and `cpu=fatal` turns cpu off instead of critical) — `Log::to_level()` now rejects
  what it does not understand; and dead `SpriteEngine::debug_log_sprite0()` (logged
  at `info`, called from nowhere) removed.
- Tests: `log_test` (10 rows) + `log_gate_test` (3 rows, drives a real Emulator
  through the port path). Both discriminative — ungate NR 0x07 and GATE-01 fails
  with 21 lines instead of 1. unit 4271/0/38 (43 suites) · FUSE 1356/1356 ·
  regression 47/0/0.
- **Correction on the record:** I initially claimed `--log-level video=warn` was
  silently turning video logging off. That was FALSE — spdlog handles `warn`
  fine. I asserted a bug I had not verified; the "guard the guard" test row caught
  it. The real defect is the narrower typo case above.
