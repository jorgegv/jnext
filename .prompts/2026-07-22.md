**01:40** — 🔴 **HEADLINE FINDING — GH #52 root-caused, and it is very plausibly
a COMMON cause across much of the #36 audit.**

**jnext had no READ handler for port $243B**, the NextREG register-SELECT port —
`src/core/emulator.cpp:3794` passed `nullptr`, so `IN A,($243B)` returned 0x00.
The VHDL requires the selected register number: `zxnext.vhd:4603`
(`port_243b_dat <= nr_register`), `:2818` (gated onto the read bus), `:2804`
(listed in `port_internal_rd_response`, so it is a **driven** read, not floating
bus).

**Why it is so damaging:** NextZXOS's per-frame ISR does `IN A,($243B)` →
keyboard scan → `OUT ($243B),A` to save and restore the caller's selected
NextREG. Under jnext it saved 0x00 and wrote 0x00 back, so **every program
launched from the NextZXOS browser had its selected NextREG silently reset to 0
(the read-only machine ID) once per frame.** Warhawk selects NR $1F and
busy-waits for raster line 191; after one interrupt it read NR $00 = 0x0A
forever → hang on the logo, no sound. With the fix it reaches the title screen
and attract mode.

**Why it hid for so long, and this is the part worth remembering:** `--load`
runs never see it, because there is no NextZXOS ISR to clobber anything. It is
only visible when a program is launched *from the browser* — which is precisely
the premise of the #36 audit, and precisely what our entire automated suite does
NOT do. Our tests load NEX files directly.

Broadcast to the other three investigators so they can re-test before chasing
subsystem-specific theories. Sent back a hardening list before review: return the
exact VHDL byte rather than "the register number" (check masking at :4603/:2818),
pin the reset/pre-write latch value from the VHDL rather than the plausible
guess, check the neighbouring `$253B` read for the identical nullptr bug one line
away, confirm it registers as a **driven** read in every machine mode so it never
falls through to floating bus, prove the rows discriminative by reverting the
handler, add an ISR-level functional row if cheap (the unit row proves the port;
what broke users was "selected NextREG survives a frame of NextZXOS"), and
**regenerate no reference screenshots** — a changed boot-nextzxos render is a
finding, not a reference to refresh. Also asked it to state explicitly which
sibling issues it has **verified** fixed versus merely expects to be.
