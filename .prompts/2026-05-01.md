## Task 1: parallax.nex investigation — RESOLVED 2026-05-01

**parallax.nex now visually matches CSpect end-to-end** (user-validated GUI).
Three deep VHDL-faithfulness coordinate-space bugs were unmasking each
other; fixing all three (plus a fourth algorithmic regression caught by
the reviewer) brings rendering to parity. Landed on main as 7-commit
series ending at `31d4424`.

Fixes (each VHDL-grounded, each unmasked the next):

1. `cde0a45` — fix(video): per-scanline change-log tag = `vc - DISP_Y`
   (32), not raw VC. Renderer iterates fb_row 0..255; tags must be in
   the same space.
2. `f5bed99` — fix(copper): cvc origin = `min_vactive` (64), not
   `DISP_Y` (32). The previous off-by-32 was masked because the
   change-log was also off by 32 — Copper-driven NR writes happened to
   land at the right framebuffer row by accident. Fix #1 surfaced this.
3. `8fcb345` — fix(layer2): clip x/y on **destination** column/row
   (pre-scroll), per VHDL `layer2.vhd:167`. jnext was clipping
   `src_x`/`src_y` (post-scroll), making the 8-pixel side gutters
   wander with scroll. Always wrong, but only visible after fixes
   #1+#2 enabled L2 X-scrolling for the bottom strip.
4. `460fac6` — fix(video): per-line snapshots indexed by fb_row +
   pre-display vblank tag coalesced to 0. Two-part fix:
   (a) the SNAPSHOT mechanism (fallback colour, ULA-enable, border
   colour, tilemap scroll) had the same +32 raw-VC-vs-fb_row mismatch.
   (b) the original sentinel-0xFFFF tag for vblank writes stalled the
   per-scanline cursor walk (`while line == log[c]`) — leading-vblank
   entries blocked all visible-row replay. Coalescing pre-display
   vblank tags to 0 lets the cursor walk normally and applies vblank
   writes from fb_row 0 onwards (matching VHDL "writes effective
   immediately"). Reviewer-flagged.
5. `68408d1` — test(regression): magic-bp-func / magic-port-func
   load NEX from canonical `test/00regression/nex/` (script bug fix).
6. `51b04b5` — test(compositor): PSCAN-VBLANK-COALESCE-01 row —
   Copper WAIT vpos=258 (raw vc=10, vblank) MOVE NR 0x68=0x80
   propagates to fb_row 0 fallback. Regression-guard.
7. `31d4424` — test(refs): rebaseline copper-demo / tilemap-demo /
   dapr-tilemap_00 references (user-authorised, visually verified).

**Final test status on main:**
- Unit tests: **33/33 suites**, aggregate 3739 / 3555 / 0 / 184.

## Task 13: per-machine vblank-top offset audit — STARTED 2026-05-01

The G164v2 fix series uses `Renderer::DISP_Y` (32, hardcoded) as the
offset to convert raw VC scanline → framebuffer row in
`Emulator::on_scanline`:

```cpp
const int fb_row = line - Renderer::DISP_Y;   // line is raw VC
```

This is correct for NEXT 50Hz / 48K / 128K / +3 because their
`min_vactive = 64` AND jnext's framebuffer top-border = 32 rows, so
`min_vactive - DISP_Y = 64 - 32 = 32 = DISP_Y` (numerical coincidence).
For other machines this ALIASES TO THE WRONG VALUE:

| Machine          | min_vactive | vblank_top (= min_vactive - DISP_Y) | DISP_Y | bug? |
|------------------|-------------|--------------------------------------|--------|------|
| NEXT/48K/128K/+3 | 64          | 32                                  | 32     | no (coincidence) |
| Pentagon         | 80          | 48                                  | 32     | YES (off by 16) |
| 60Hz overrides   | 40          | 8                                   | 32     | YES (off by 24) |

Visible effect on Pentagon / 60 Hz: any per-scanline-replayed
mid-frame write to palette / layer2 / sprites / ULA / tilemap (and
the snapshot mechanism for fallback / ULA-enable / border /
tilemap-scroll) gets applied at the WRONG framebuffer row. Currently
masked because no Pentagon or 60 Hz demo in the regression suite
exercises the per-scanline replay machinery in a visible way — but
the fix is mechanically wrong on those machines.

**Sites to audit and fix** (find via `grep -rn "Renderer::DISP_Y" src/`):
1. `Emulator::on_scanline` — change-log tag and snapshot index
   should use `(min_vactive - DISP_Y)` instead of `DISP_Y` directly.
2. `Emulator::run_frame` end-of-frame snapshot — uses `FB_HEIGHT-1`
   directly (machine-independent, OK).
3. Any other coordinate-conversion site that hard-codes `DISP_Y`
   when it should be the per-machine vblank-top.

**Plan:**
1. Audit all `DISP_Y` use sites and classify each as
   (a) framebuffer-geometry constant (correct) vs
   (b) raw-VC-to-fb-row conversion (needs vblank_top = min_vactive - DISP_Y).
2. Add a `VideoTiming::vblank_top()` accessor returning
   `min_vactive_ - Renderer::DISP_Y` (or expose `min_vactive_`
   directly and let callers compute).
3. Replace category (b) sites with the accessor.
4. Add unit tests asserting Pentagon + 60Hz tag/snapshot indices
   are correct. (PSCAN-PENTAGON-MV80 / PSCAN-60HZ-MV40.)
5. Verify regression on main is still 32/0/0 (no NEXT-50Hz behaviour
   change expected because DISP_Y == vblank_top for that machine).
6. Independent reviewer.
