## Step 3 — V22-NMP-01 VHDL verification — **FINDING IS WRONG**

### Audit claim

> "VHDL zxnext.vhd:5601-5605 has the `nr_c2_we` / `nr_c3_we` write
> strobes commented out — the write decoder at :4860+ NEVER fires the
> elsif arms at :2064-2067 that would latch the byte from nr_wr_dat."

### Reality

VHDL has **two** write-decoder processes for NextReg-port writes:

1. **Process A (combinatorial, lines 4786-4914)** — generates the
   `nr_*_we` strobes:
   ```
   process (nr_wr_en, nr_wr_reg)
   begin
      nr_c2_we <= '0';
      nr_c3_we <= '0';
      ...
      if nr_wr_en = '1' then
         case nr_wr_reg is
         ...
            when X"C2" => nr_c2_we <= '1';    -- LINE 4894 — NOT COMMENTED
            when X"C3" => nr_c3_we <= '1';    -- LINE 4895 — NOT COMMENTED
         ...
   ```

2. **Process B (clocked, lines 4926+)** — uses the strobes (or fires
   directly via its own case statement). The lines at :5601-5605 the
   audit cites are inside this second process, in a comment block:
   ```
   --             when X"C2" =>
   --                nr_c2_we <= '1';
   --             when X"C3" =>
   --                nr_c3_we <= '1';
   ```
   These commented-out lines are **vestigial duplicates** — the
   strobes are already generated by process A, so the comment-out is
   merely a stylistic dead-code cleanup. The same pattern applies to
   many other registers in process B (NR 0x02 at :5118, NR 0x69 at
   :5453, NR 0x80 at :5488-5489, MMU 0x50-0x57 at :5415-5416, etc.) —
   all of which have ACTIVE strobe generation in process A and are
   unambiguously functional registers.

### The latch process at :2054-2070

```
process (i_CLK_28)
begin
   if rising_edge(i_CLK_28) then
      if reset = '1' then
         nr_c2_retn_address_lsb <= (others => '0');
         nr_c3_retn_address_msb <= (others => '0');
      elsif (Z80N_command_s = NMIACK_LSB) and cpu_wr_n = '0' then
         nr_c2_retn_address_lsb <= cpu_do;
      elsif (Z80N_command_s = NMIACK_MSB) and cpu_wr_n = '0' then
         nr_c3_retn_address_msb <= cpu_do;
      elsif nr_c2_we = '1' then              -- LINE 2064 — REACHABLE
         nr_c2_retn_address_lsb <= nr_wr_dat;
      elsif nr_c3_we = '1' then              -- LINE 2066 — REACHABLE
         nr_c3_retn_address_msb <= nr_wr_dat;
      end if;
   end if;
end process;
```

The elsif arms at :2064-2067 ARE reachable. Every CPU NextReg-port
write to NR 0xC2 fires `cpu_req=1` → `nr_wr_en=1` → process A asserts
`nr_c2_we=1` → latch process loads `nr_c2_retn_address_lsb <= nr_wr_dat`.

The priority chain in the if/elsif means that **simultaneously** with
an NMIACK_LSB, the NMIACK path wins (highest priority). But in the
absence of an active NMIACK, software CAN write the latch via the
NextReg port, and the read mux at :6232-6236 returns that written value.

### Comparison with Pass-8's RO-guard (the precedent V22-NMP-01 claims to extend)

| NR | `nr_XX_we` signal declared? | Strobe in process A? | RO in VHDL? |
|---|---|---|---|
| NR 0x01 | NO (no `nr_01_we` signal anywhere in zxnext.vhd) | NO | ✓ truly RO |
| NR 0x0E | NO (no `nr_0e_we` signal) | NO | ✓ truly RO |
| NR 0x0F | NO (no `nr_0f_we` signal) | NO | ✓ truly RO |
| **NR 0xC2** | **YES (`nr_c2_we` declared at :1080)** | **YES (asserted at :4894)** | **NO — writable from NextReg port** |
| **NR 0xC3** | **YES (`nr_c3_we` declared at :1081)** | **YES (asserted at :4895)** | **NO — writable from NextReg port** |

NR 0x01/0x0E/0x0F have NO `nr_XX_we` signal AT ALL — they were
correctly RO-guarded in Pass-8. NR 0xC2/0xC3 are STRUCTURALLY
DIFFERENT — they DO have `nr_c2_we`/`nr_c3_we` signals AND active
strobes. Pass-22 misread the comment-out at :5601-5605 (vestigial,
inside process B) as if it were the only strobe location, missing the
ACTIVE strobe assignments at :4894-4895 in process A.

### Conclusion of Step 3

**Pre-fix jnext was VHDL-faithful** — the fall-through `regs_[reg]=val`
assignment matches the VHDL latch behavior (modulo the NMIACK priority,
which is irrelevant for steady-state software writes). The Pass-22 fix
**injects a divergence** that breaks the spec-correct behavior.

### Sandwich verification

Performed sandwich (revert RO-guard extension → run tests → restore):

1. With fix active: nextreg_integration 278/278 PASS.
2. With RO-guard extension reverted (only NR 0x01/0x0E/0x0F guarded):
   - V22-NMP-01-A FAIL: `before=0x00 after=0xaa` (write succeeded — the
     spec-correct behavior)
   - V22-NMP-01-B FAIL: `before=0x00 after=0x55` (write succeeded)
   - V22-NMP-01-D-LSB FAIL: `lsb=0xff expected=0x34` (post-NMIACK write
     overwrote the latch — exactly what VHDL would do for the
     `nr_c2_we`-fired elsif arm)
   - V22-NMP-01-D-MSB FAIL: `msb=0xff expected=0x12` (same)
   - C-LSB / C-MSB still PASS (NMIACK pathway unaffected)
   - Total: 274 pass / 4 fail.
3. With fix restored: 278/278 PASS.

The 4 failures **PROVE** the divergence. The test direction was set by
the wrong audit reading. **The tests should be flipped**: writes to
NR 0xC2/0xC3 SHOULD update the read-back, and the test should assert
the after-value matches the written byte.

## Step 4 — Side-effect inspection

- **NextZXOS boot path use of NR 0xC2/0xC3**: not directly observable
  (these registers are dedicated to the stackless-NMI return-address
  latches; NextZXOS itself unlikely to write them via NextReg port).
  Practical user-visible impact of the wrong fix: ~zero.
- **Save / load**: `NextReg::save_state` / `load_state` use direct
  `regs_.data()` bytes read/write (lines :493-517), bypassing
  `NextReg::write`. The RO-guard does NOT affect save/load.
- **Other test files**: nextreg_integration_test is the only test
  touching NR 0xC2/0xC3 writes via the public `write()` API. No
  collision with the V22-NMP-01 rows.

Practical impact of the wrong fix is **inert** in steady state, but
it's a wrong-direction "class-(c)" — fixing it took jnext from VHDL-
faithful to VHDL-divergent.

## Verdict

**REJECT**

Reasons:
1. V22-NMP-01 misreads VHDL. The commented-out `nr_c2_we`/`nr_c3_we`
   at zxnext.vhd:5601-5605 are vestigial duplicates inside process B
   (clocked register update process). The ACTIVE strobe generation is
   in process A (combinatorial, :4894-4895) and is NOT commented out.
2. The elsif arms at :2064-2067 ARE reachable. NR 0xC2/0xC3 ARE
   writable via the NextReg port path per VHDL.
3. The fix (adding 0xC2/0xC3 to the RO-guard) introduces a NEW
   divergence from VHDL where none existed pre-fix.
4. The 4 of 6 new test rows (A, B, D-LSB, D-MSB) enshrine the wrong
   contract; they would FAIL on real hardware via DZRP.
5. Pre-fix jnext (with bare `regs_[reg]=val` fallthrough) was
   ACCURATELY modeling the VHDL behavior — the only divergence vs.
   real hardware was the NMIACK-priority case where simultaneous
   NMIACK + NR-port write would behave differently (NMIACK wins in
   VHDL; in jnext both paths just touch the same `regs_[]` byte). But
   that's a stale-byte edge case that doesn't matter in practice.

### Required corrective action (for the audit-fix iteration)

1. **Revert** the `reg == 0xC2 || reg == 0xC3` addition in
   `src/port/nextreg.cpp:456-458` — restore the Pass-8 guard to
   `NR 0x01 / 0x0E / 0x0F` only.
2. **Flip the test direction** in `V22-NMP-01-A`, `V22-NMP-01-B`,
   `V22-NMP-01-D-LSB`, `V22-NMP-01-D-MSB`. Either:
   - Rewrite to test the spec-correct contract (write-then-read must
     match for NR 0xC2/0xC3 via NextReg port, per VHDL :2064-2067 +
     :4894-4895), OR
   - Remove the WO/RO-direction tests entirely and keep only C-LSB /
     C-MSB (which already test the NMIACK-pathway write semantics).
3. **Withdraw V22-NMP-01** from the audit report; mark Pass-22 as
   yielding **0 findings** (which would be a "convergence" pass for
   NMI/MF/Port).
4. **Re-run** Pass-22 with the corrected understanding — or treat
   this pass as converged.

### Severity classification

This is a class-(c) **regression** (not a class-(a)/(b) — no boot or
behavioral change is gated on NR 0xC2/0xC3 NextReg-port writes in
NextZXOS). However, the FIX-DIRECTION is wrong: jnext is now LESS
VHDL-faithful than before. The wrong tests **enshrine** the wrong
contract, which is a higher-grade defect: future audits will assume
this is correct and propagate the error.
