    7.10 C frames and values¶

    7.9 holds the records, the storage and the scopes. This page is what sits on them: the C frames at a stop (Debugger::c_frames()), and the rule that keeps the call-stack tracker running for them. Reading a value (the formatting layer, the type lookup, the C paths, the facade that returns rows) is the next stage of the epic and is not described here yet.

    The frame base¶

    Every compiler keeps a frame base fp, the address of the saved frame pointer. Write E for the SP at the function's entry instruction (the address of the return address): then fp = E - 2, for all three compilers, and the B records of a variable are offsets from fp.

    Compiler How fp is kept Evidence
    sccz80 (2.4 and master) call l_debug_push_frame at the entry stores E - 2 in __debug_framepointer; the caller's fp is at [fp] z88dk/libsrc/l/sccz80/8-8080/l_debug_push_frame.asm; the vars.c listing of master/sccz80-cvars
    zsdcc push ix; ld ix,0; add ix,sp (DD E5 DD 21 00 00 DD 39), so IX = E - 2; [IX] is the caller's IX the vars.c listing of master/sdcc-cvars
    80cc per function: some use IX, some l_debug_push_frame master/80cc-cvars (sum and main IX, other push-frame) and master/80cc-fc
    banked banked_call pops its own return address and call l_jphls into the function, so E holds the return address into banked_call and the arguments sit above it z88dk/libsrc/target/zxn/far/zxn_banked_call.asm
    the epilogue after call l_debug_pop_frame the variable already holds the CALLER's fp; after pop ix IX is the caller's. SP is E only right after that instruction: a __z88dk_callee routine pops its arguments between it and the ret (fc listings of all three compilers), so from the next instruction on the base is not known without the tracker the same listings

    The helpers (__debug_framepointer, l_debug_push_frame, l_debug_pop_frame) are joined by public name in CFrameHelpers (struct CFrameHelpers, variable_store.h:111), by the adapter (helpers.framepointer, z88dk_source_map.cpp:676), never from the symbol table: a hand-loaded map attaches no symbols. They are unresolved, with a reason, in a zsdcc map.

    Which function a PC is in¶

    A function's extent is a list of pieces (CPiece, variable_store.h:57). fill_extents() (z88dk_source_map.cpp:328) bounds the extent above by the lowest map value, in the same section, of another function's entry, a symbol or line record of another module, or the section's __<section>_tail; then it splits [entry, bound) at the 8 KB logical boundaries and places each piece with the rule the symbols use. A function that crosses a slot lives in two spaces (a NEX code group is placed slot by slot: page 4 for $8000-$9FFF, page 5 for $A000-$BFFF). With no bound, pieces is empty and extent_why says so: the function then contains no PC.

    VariableStore::locate() (variable_store.cpp:52) answers "which function, and how far into it" from a SourceAddress: the piece with the same space whose range holds the address. Nothing else is used, neither the nearest symbol nor a jump target. The scope tables follow the same rule (fill_scopes(), z88dk_source_map.cpp:377): a record is filed under the function of its module and section whose entry value is the greatest at or below the record's, and each CScope carries its offset from the entry, so tables compare across pieces. Comparing spaces would lose the tail of a function that crosses a slot (cross.c, in the *-cross fixtures).

    The frames¶

    Debugger::c_frames() (debugger_cframes.cpp:30) returns the frames newest first. Frame 0 is where the CPU is; the CFrame (struct CFrame, debugger.h:1228) has its function (an index into variables()->functions(), -1 for assembly), the pc, the source line and the base, with how it was found:

    • Tracked. With the tracker's frames (oldest first, n of them), frame k was entered by frames[n - 1 - k], whose sp_at_call is E, so fp = sp_at_call - 2. The PC of an older frame is the CALL that is in progress (caller_pc in caller_space), which is inside the call, never the return address. The function is the one that contains that PC, never the target_pc: the banked case's target is l_jphl. An INT or NMI frame fits the same rule.
    • Prologue (frame 0, no tracked frame): the entry bytes decide. A call to l_debug_push_frame: at the entry fp = SP - 2, right after call l_debug_pop_frame the same, otherwise peek16(__debug_framepointer). The IX form: at the entry fp = SP - 2, after the push ix and after the ld ix,0 fp = SP, right after pop ix fp = SP - 2, otherwise IX. "Right after" is tested from the bytes before the PC, so a long function costs nothing. Between the restore of the caller's base and the ret (found by walking the function's code from its entry, in_epilogue(); a ret closes the window), any other PC is Unknown with a note. The code is Unknown too when it cannot be read (Epi::Unsure, a defensive state that no fixture reaches and no row covers); a walk that steps over the PC without landing on it is taken as outside the window.
    • Chain (older frames): ret = peek16(fp + 2), the next PC is ret - 1, and the next fp is peek16(fp) only when the next function keeps its frame in the same style, and that style is a push-frame or an IX frame (a function with neither saves no frame pointer). A change of style ends the walk, the frame listed Unknown with a note (80cc mixes both styles); a next PC in no C function is listed as assembly and stops the walk; so does a next fp that is not a stack address above this one.
    • Unknown: none of the above applies, note says why.

    Each frame has a floor, the lowest stack address that holds its data: SP for frame 0, the inner call's sp_at_call + 2 for an older frame. A B slot at fp + offset, offset < 0, is allocated only when it is at or above the floor. "Outer frames are always allocated" is wrong: a stop inside l_debug_push_frame, or in any assembly routine a function calls before it allocates its locals, leaves that function's locals unallocated.

    Who keeps the tracker running¶

    The tracker (CallStack, 7.5) costs per instruction, so it is not always on. Its state is derived (Impl::sync_call_stack(), debugger_session.cpp:128), the one writer, from two things:

    1. A client's own request. Debugger::set_call_stack_enabled(by, on) (debugger_inspect.cpp:906) sets the request on that client's row. The tracker is on while any live client asked. One client switching off no longer takes another's tracking away (the Qt debugger window closing used to empty a ZRCP session's extended stack), and a detach drops the request with the client.
    2. The source map. With no request, tracking is on while the live source map has C variable records and a live non-observer client is attached (the Qt emulator window's permanent observer does not count).

    sync_call_stack() reads the client list and the live source map directly (never recheck() or the replay-guarded clients_attached()), so it cannot recurse, and it runs wherever an input changes: a request, an attach or detach, recheck(), a source map loaded or cleared, the program sidecars, a reconstruct. CallStack::set_enabled() empties the tracker only on a change, and the backend writes it only when the derived state changes (or, after a reconstruct, whenever it is on): a write made outside the backend, directly on the Emulator (CTL-12-55, QEN-01), is not undone by an attach or an in-place landing that changes nothing derived. call_stack_enabled() returns the effective state.

    Formatting a value (the pure layer)¶

    src/debug/c_value.{h,cpp} turns a type chain and bytes into text and knows no machine: a CReader callback supplies bytes (the CPU view for the stack and for pointer targets; the caller picks), so every rule is pinned with synthetic memory in c_value_test (CVALF-*). Reading a value on a running machine through the page-aware identity, and the facade that returns rows, are the section after this one.

    Formatting is locale-independent: every number goes through std::to_chars, never a printf-family call or an ostream (QApplication runs setlocale(LC_ALL, ""), and on a Spanish host %g prints 1,5; CVALF-09).

    Type (decoder) Text
    SC 65 'A' for 0x20..0x7E, else the number; signed or unsigned by :S / :U
    SI, SL, bare :S/:U little-endian, {size} bytes (1, 2, 4, 8), decimal
    SF with a format the module's float format decides (c_float_format(): CFormatCtx::module, the module of the variable's record, which a path walk never changes, so a pointer's target and a struct's member read in the variable's module's format). Modes: 0 z80 and 2 mbf32, 3 mbf40, 4 mbf64 are ms mantissa bytes (sign in bit 7 of the last, implied leading 1) then the exponent byte, value = 0.1mmm(binary) x 2^(e - bias), exponent 0 is zero; 5 z88 (BBC) is the same one byte later (byte 0 unused), exponent byte 0 being a 32-bit two's complement integer in the mantissa bytes (ms 4 only); 6 am9511 is 24 mantissa bits with the leading 1 stored, then a sign bit and a 7-bit two's complement exponent; 1 ieee is binary32 (bias 126, ms 3).     struct {x = 3, y = 4, tag = 5}, nested, from the T: record

    c_find_type() (c_value.cpp:701) finds a struct's T: record: the records of the variable's own scope first (zsdcc's copy per module), then those of its module, then a tag that is unique across all records (sccz80 and 80cc: one per header). Different definitions at the deciding step are ambiguous, never first-wins. c_type_text() (c_value.cpp:694) prints char, unsigned int, struct node *, int [2][3], int (*)(); the CDB has no union marker, so a union is struct word, and no typedef name survives. A zsdcc padding member (__00000000) is not shown.

    A struct's size is a declared object's when there is one: an S: record, or a struct member, whose chain is exactly ST<tag> ({2}STflags for g_flags). With none, it is the members' extent, provided no member shares bytes with another (a union is fine). sccz80 and 80cc write a bitfield as an int that sticks out of the struct (z88dk U2): struct flags is 2 bytes but its member hi is an int at offset 1, so for such a struct the members' extent overstates the size and is not used: with no declared object it is refused as size unknown (z88dk U2). Every view of such a member (the whole struct, a member path, a pointer, an element p[1], a member of a nested struct) clamps its read to the struct that holds it and zero-fills the overhang, so hi is 200 for the bytes 8D C8 whichever way it is reached, and no read goes past that struct.

    c_parse_path() (c_value.cpp:788) parses the C paths: ['*'] primary {'.' name | '->' name | '[' index ']'}, the primary a name, fn::name, file.c::name or file.c::fn::name (the file names which fn when two modules have a function of that name), the index decimal, 0x<hex> or $<hex> with no sign. A leading # is refused: c_parse_path(text, allow_handle) accepts #<n> (an index into VariableStore::variables(), followed by the usual steps) only for the Variables panel's own rows, which reach the facade through write_c_value_row() and c_children_row() (a read of a row is the row's own value, already in the CValueRow); every typed surface (watches, scripts, ZRCP, GDB) uses the plain functions and so cannot name a handle, which is an index that means another variable after a rebuild. As in C the postfix operators bind tighter than the *: *x[1] is *(x[1]) and *head->next is *(head->next). c_eval_path() (c_value.cpp:900) walks the steps over a typed location (an array index is checked against its count, a pointer index scales by the element size, the size of a pointed-to array is its whole size, a null pointer is refused), then applies the *, and c_read_loc() reads and formats it. Every refusal says why.

    c_visible_locals() lists which locals show at a PC: the parameters (ordered by stack position), the locals, the static locals. A parameter is a record of level 0 (sccz80, 80cc), at a stack offset >= 4, or (zsdcc) in a block below the body's first block (the entry scope's), where its register and fastcall parameters sit. Parameters and level-1 locals are always visible. Which block is open depends on the compiler:

    • zsdcc (and a synthetic store): a local of level >= 2 is visible iff its block is the open block or one of its ancestors. A block's level is its locals' own; a block that holds no local takes the level of the first scope entry, in offset order, that names it. The open block is the greatest known block at the scope's level at or below the scope's block. With no block data or an unknown scope, every block local is shown, marked scope unknown.
    • 80cc: cc80_verdict() answers Hidden or Unknown, never plain, and only when CFunction::scopes_from_listing is set (the function's records carry levels, as z88dk master writes them from 2026-11-04, and a listing covers it) and the PC's scope is known; otherwise every block local (level >= 2) is listed, flagged scope unknown (a note on reads, a refusal on writes) and never hidden. fill_listing_scopes() replaces the function's scope table with every C_LINE directive of the listing, each at the first byte row after it (the last directive before the row owns it; Z88ZB-12, Z88ZB-13, Z88ZB-14), because the map keeps one symbol per (line, scope) and 80cc repeats lines in loops. Why never plain: 80cc stamps some code with the scope of another block (H-a to H-c, 7.9), so a PC's scope does not prove its block locals in scope (CVZB-20 pins fourteen functions). What the stamp proves closed is closed (checked on every program of the rows) and is hidden. The rule (E = the trail's known entries of level >= 1, s = the PC's line, level, block): F1 b > B_s is closed; F2 b == B_s and lv > L_s is closed; F3 a line x of b, then an entry of a lower block strictly between x and l_s, closes b (CVZB-18); F5 an open block (B_s or an ancestor, the lowest block being every block's ancestor and a < b one when a line of a is after a line of b) numbered above b with a level <= lv puts v outside its scope. At a then-branch's closing jump, hides are relative to the else part's stamp, so a then-branch local can be hidden there; the Source tab shows that jump on the else line too. Everything else is scope unknown. No heuristic (taking the least level of a block as its own shows i plain inside j's loop). Without exact scopes the generic rules are wrong on 80cc (measured on 80cc built at upstream 96c0efaddd: a closed sibling shown, the variable in scope hidden, no note), which CVZB-15 pins.
    • Shadowing: c_pick_local() picks, among the visible locals of a name, the greatest (level, block), as gdb does; certain is false when a candidate is scope unknown. find_local() uses it: a read of an uncertain pick carries c_ambiguous_note() (Found::ambiguous), a write to it is refused by the scope unknown guard (an uncertain pick is always a flagged row: only level >= 2 variables are flagged and the innermost candidate has the greatest level; CVZB-16 and CVZB-20 assert it), and c_locals marks every other candidate shadowed (may be shadowed when uncertain), which monitor locals prints as [shadowed]. cvar() and ZRCP carry no notes and return the innermost. CVZB-19, SRCDBG-ZB-14 to -16, GDB-ZB-02. A static local of level >= 2 (a block static) goes through the same visibility test as a block local of its (level, block) in c_visible_locals(): the sccz80 walk, zsdcc's exact blocks, the 80cc rule (hidden or scope unknown); a level-1 static is listed at every PC (CVZB-21, SRCDBG-ZB-18 to -20).
    • sccz80 with a trail (replay_trail()): the trail is replayed up to the PC's offset as a stack of open blocks, stack[level] = block | SKIP. A record at a level drops every level above it. A record that names a block higher than any seen fills the unset levels below it with the greatest unseen block of that level in between (a block opened and closed without a line of its own, or the block a for opened: it is named by nothing but its header variable's S: record), else SKIP; a record that names a lower block than the stack holds at its level leaves the stack alone (the pre-2026-11-04 numbering, the last block opened: c_trail_disagreements() counts those, 0 on every fixed build). A local is visible iff the stack holds its block at its level, or, when its block's level is lower than its own (a for (int i ...) variable on 2.4 and before z88dk master of 2026-11-04 carries the enclosing block's number), iff that block is open and every level between is SKIP. A block's level is the first trail entry that names it, else its locals'. The replay is the same on records where a for opens a block of its own (z88dk master from 2026-11-04: the for line stays in the enclosing block, the body is level + 2 with the next number, CVZB-14): its variable is visible in the body and a closed sibling that shares its slot is not. The for line itself is recorded in the enclosing block, so the loop variable is hidden on that line.
    • The guard (CLocalRef::shares, c_shares_note()): every pair of visible B-space variables whose byte ranges overlap is marked, each naming the other, and neither is hidden. c_locals rows and read_c_value carry the note; a write is refused. c_children rows do not carry it (a member of a shared aggregate shows no note, but its write is refused).

    c_read_register_local() (c_value.cpp:1395) reads an R local of frame 0 ([c,b] is C | B << 8, with a note that it may be stale), refuses [] as optimised out and an outer frame as not available. c_fastcall_records_nominal() is the U1 rule, per function: true iff the function is fastcall and none of its parameters (level 0, space B) is recorded at a negative offset, that is, the records are the pre-2026-11-04 ones, every parameter at its nominal slot, where none of them is. Fastcall is CConv::ListedFastcall (a listing flags it), or the caller's prologue_fastcall for a function no listing names (a listing that names it without the flag wins). CVALF-30 pins the rule's boundary cases on a synthetic function: a level-1 local at a negative offset does not count, offset 0 is nominal, a hidden record is ignored, an R-space parameter alone is not nominal, and a listing that names the function without the flag wins over the prologue.

    Reading values: the facade¶

    Debugger has six CAP-SRC readers (debugger.h), all const, all running recheck() first (through variables() and c_frames()) and bumping nothing themselves, so a panel redrawing on state_revision() does not redraw on a read:

    Reader Gives
    c_variables_status() (debugger_cvalues.cpp:491) {available, why} with a printable reason: no source map is attached; an SLD source map carries no C variables; the map has no C debug records (lines from listings only); zsdcc wrote no C variable records for this build (zcc -O0 keeps the C_LINE records and writes no __CDBINFO__, fixture master/sdcc-cvars-O0); the map has line records but no __CDBINFO__ records; all N C variable records were refused: <reason>; a stale map
    c_locals(frame) (debugger_cvalues.cpp:527) the parameters (by stack position), the locals visible at the frame's PC and its static locals, each a CValueRow (path is the name, except for a row that another visible variable of its name shadows: its path is its internal handle, name_path is empty because no typed name reaches it, and the row carries the note shadowed, or may be shadowed when the pick is not certain; a static whose function::name is shared has ambiguous_path set); refused, with a reason, for a frame past the end, an assembly frame or a frame whose base is not known
    c_globals() (debugger_cvalues.cpp:575) every global, file static and static local, ordered by file then name, with a path no local can shadow: vars.c::s_dup, sum::calls (a.c::init::done when two modules have a function init). When two block statics of one name share their function (f::n twice, zsdcc), each row's path is its internal handle, name_path is the shared typed path and ambiguous_path is set: a typed read or write of f::n is refused (ambiguous: 2 statics named n in f)
    read_c_value(frame, path) (debugger_cvalues.cpp:617) the object a C path names in that frame: ok or why, the type text, the value text, notes, the typed location loc, where, integer (Char, Int, Long, Scalar, Bitfield and Pointer: the address) and real (the floats)
    c_children(frame, path, first, max) (debugger_cvalues.cpp:713) what a tree lists under an object: a struct's members, an array's elements first..first + max (total is the element COUNT), a pointer's pointee (a struct's members as p->x, anything else as p[0], named *); void *, a function pointer and a scalar have none (ok, total 0). Each row's path is the parent's plus a suffix and round-trips through read_c_value (through c_children_row() when its root is a handle) (for a *E path the base is E[0], since the grammar applies a leading * after the postfix steps: *p + .x would read *(p.x)); a row is read, placed and noted exactly as read_c_value would, so a banked global's elements carry its page. !ok gives read_c_value's own reason, or null pointer / the unreadable address. The root variable's scope unknown, shares and ambiguous notes are added to every child row whose read succeeded, as read_c_value() adds them; a child of a handle path has an empty name_path. c_children_row() and write_c_value_row() take the panel's row paths, which may be handles; the plain functions refuse them.

    The children come from the pure c_children() (c_value.cpp:1013; CChild, CChildren): a struct's visible named members in record order (an unnamed C11 member has no path and is left out), an array's elements scaled by the element size, one pointee for a pointer.

    A CValueRow carries name, path (which round-trips through read_c_value, or through c_children_row() and write_c_value_row() when it is an internal handle), name_path (the typed path that reaches this variable, empty when none does, as for a shadowed local), ambiguous_path (the typed path names more than one static), file, type, kind (Param, Local, StaticLocal, FileStatic, Global), where, ok with value or why, aggregate and notes. A failed read has an empty value, never 0. where tells a page address (Page: the space and the 16-bit logical address, also DivMmcRam) from a CPU address (Cpu: a stack slot, what a pointer points at) and from registers (Register: BC).

    Where an object is read from (eval_var(), debugger_cvalues.cpp:178):

    • A global, file static or static local is read from the page its map symbol was placed in (CStorage::at; the reader is space_reader(), debugger_cvalues.cpp:104), whatever the MMU maps there now, and an element or member of it too. A note says page 20 is not mapped at $C000 now when it is not mapped. A value that would cross the end of its 8 KB page is refused (the value crosses a page boundary, with no value: a failed read is never 0).
    • A stack variable is at the frame's base fp plus its record's offset, through the CPU view; a negative offset below the frame's floor is not allocated.
    • A register local is frame 0's register, with the note that it may be stale; in an older frame it is not available (register, outer frame); R [] is optimised out. A pointer held in a register can be followed (*p, p->x, p[i] start at the pointed-to object, read through the CPU view, CLoc::ptr_value); a member or an element of a register-held aggregate has no address and is refused.
    • What a pointer points at is read through the CPU view (C semantics), which is why a location carries rooted: true while it is inside its root object, cleared when a pointer is followed (CFormatCtx::read_root).
    • A parameter of a function for which c_fastcall_records_nominal() holds is location unknown (z88dk U1...). The prologue evidence is read by prologue_is_fastcall(): the function's entry bytes call l_debug_push_frame; push hl (or push de; push hl), CD <lo hi> E5, l_debug_push_frame being the helper the store resolved, read through the entry's own page (peek, no side effect). KNOWN LIMITATION: a float or long long fastcall argument is pushed by other helpers (gen_push_float, llpush), so with no listing a function that takes one is read from the nominal slot, a wrong value; with a listing it is refused.
    • A stack variable of an 80cc function carries the note 80cc may not keep it in the frame slot its record names: the value shown can be stale or another variable's, in every frame and on members and elements (CCompiler::Cc80). It is always on: nothing in the map says whether the build has z88dk master's 2026-11-04 fix, and a parameter the function reassigns is still wrong after it.
    • A float of a module with no recorded format (zsdcc, assembly, z88dk 2.4, master before 2026-11-06) decides by size, as before, and a map whose float library is mbf32, mbf64, bbc or dai32 is refused (float format <lib> is not read: ...): the record says only {4}SF. math32, am9511, math48 and a map that names none decide by size. A pointer to such a float has no size and is refused. A module that records a format (the SF row above) never reaches this rule, whatever library the map names. A struct looked up in another module (the unique-tag step of c_find_type()) whose float members, directly or nested, are not the width of the object's module's format is refused with struct <tag> is laid out with <n>-byte floats (module <m>); this object's module <h> uses <w>-byte floats (struct_layout_refusal()): the value, its members, its children and its size.
    • A bitfield's type text is int :N for an SB..:S record and unsigned int :N for :U (a plain int bitfield is :U in sccz80 and 80cc, :S in zsdcc). An {-1} array is refused an array of unknown length: its debug record has no size.

    find_var() (debugger_cvalues.cpp:352) resolves a name in frame k: the frame's visible locals, then its function's static locals, the file's statics, the globals. A local that exists but is hidden is out of scope at <file>:<line>. fn::name names a static local from any frame, and a local of fn only from a frame of fn; file.c::name names that file's statics and globals.

    The int32 atom: c_int32_scalar()¶

    c_int32_scalar(loc, integer) (c_value.cpp:1485) is the one rule for what a C value is as a 32-bit integer; the script atom cvar() and, through its translation, ZRCP's CVAR() both reach it through the evaluator, so there is nothing to keep in step. It reads loc.type (the head of the chain and the size) and loc.note, so a register-held value (no address) passes a CLoc with just its type, which read_c_value() fills for it. integer is the facade's CValueResult::integer.

    The object Result
    Char, Int, Long, Scalar, Bitfield, Pointer, size at most 4 the low 32 bits of integer: an unsigned 32-bit value keeps its bit pattern (0xCAFEBABE is -889275714, as the DSL's literal is), a pointer is its address
    the same kinds, size over 4 ({8}SL) refused: a <size>-byte integer does not fit the script's 32 bits
    Float, Float16, Fixed refused: <type> is not an integer (the DSL has no floats; truncating would be a guess)
    Struct, Array refused: <type> is an aggregate, not a scalar: name a member or an element
    Void, Function refused: <type> has no value
    a loc.note (a member of an overlapping struct, z88dk U2) refused with the note: the value is not trustworthy
    integer empty refused: no integer value was read

    The register-local "may be stale" and "page N is not mapped" notes are row notes, not CLoc::note, and do not refuse: they say how far to trust a value that is shown. The rule is a pure function, so CVINT-01 and CVINT-02 reach every arm with synthetic types; no fixture has an 8-byte integer, a binary16 or an _Accum global.

    Writing a value¶

    write_c_value(by, frame, path, CNewValue) (debugger_cvalues.cpp:642) is the one write, and it takes its place from the read: a write needs a successful eval_var() of the same path, and its bytes are that read's loc and where, so there is no second resolver to drift from the first. Whatever a read refuses a write refuses with the read's own words (U1, a frame base that is not known, not allocated, optimised out, a null pointer, an index past the end, a page crossing, an unresolved storage). The write adds six refusals, in this order:

    Refusal Why
    scope unknown (Found::scope_unknown, copied from CLocalRef in find_local()) JNEXT cannot place the block of an 80cc local (a for variable, a local under a for, a case the records cannot tell, or no listing beside the map, or a build before z88dk master of 2026-11-04), so the slot of a block local may hold another variable: a note for a read (read_c_value() adds scope unknown: ... beside the row's), a refusal for a write
    shares its stack slot with <name>: ... (Found::shares, from CLocalRef in find_local()) the variable's slot overlaps another listed variable's: the write would land in the other
    a register variable cannot be written a root with record space R, and a path that follows a register-held pointer: the record gives no live range, so the register may hold another value by then; registers_of() names them
    <type> is an aggregate: write a member or an element a struct or an array, char arrays included (no string assignment: its read-back would depend on how a string with a NUL prints)
    the loc.note a member of an overlapping struct (z88dk U2): the place is not certain
    the encoder's refusal below

    The current bytes are peeked through where (Page: peek(space, space_offset(...)), Cpu: the CPU view), the encoder makes the new ones, and exactly one poke() writes them: one MUTATE line and one state_revision() bump, and neither on a refusal decided before the poke (it writes, logs and bumps nothing). A write that lands only some of its bytes (a 2-byte object on $3FFF, half in ROM) is RefusedReadOnly with the one MUTATE line and the one bump of the bytes that landed; a refusal by poke() before a byte lands (RZX, a read-only page, DivMMC RAM) has neither. The status is poke's own: RefusedRzx, RefusedReadOnly (with landed, worded K of N bytes landed (the rest is read-only)), InvalidPage or Unsupported; every refusal decided before it is RefusedUnavailable with the reason in why. There is no C-specific code. A dot command's global lives in DivMmcRam, which poke() refuses (identity_only(), INS-02-30), so it is Unsupported with DivMMC RAM bank 2 cannot be written by the debugger (unsupported). After an Ok the object is read back into CWriteResult::value. CWriteResult::notes holds the notes of the read that preceded the write (the 80cc frame-slot note, a not mapped note): the Qt edit message and GDB monitor set var print them. A Page object cannot half-land: the read already refused a page crossing.

    c_encode_value(type, CNewValue, current, avail) (c_value.cpp:1792) and its overload with a CFormatCtx, which the facade calls, are pure, with no printf or ostream (the c_value.h rule: locale independent). CNewValue is a text a person typed (the Qt panel, ZRCP, GDB) or a script's 32-bit value:

    Type Text Int32 (a script)
    Char, Int, Long, Scalar of 1 or 2 bytes, Bitfield the type's range by sign (a bitfield: the field's width), else '<text>' is out of range for <type> (<lo>..<hi>) the same
    the same, 4 bytes the strict range any int32, as its 32-bit pattern (the mirror of c_int32_scalar())
    the same, 8 bytes the int64 / uint64 range refused: does not fit the script's 32 bits
    Pointer 0..65535 0..65535

    {6}SF (z88dk 48-bit, no format) rounded to nearest; refused when the exponent leaves 1..255 (encode_float48(), c_value.cpp:1727) refused: float is not an integer
    {4}SF (binary32) the C library's strtof through an istringstream (correctly rounded), out of range refused refused
    S6 (binary16) through float, nearest even, refused when it rounds to infinity or to zero (encode_float16(), c_value.cpp:1758) refused
    SQ refused: fixed-point layout not decoded refused

    A text is trimmed, then an optional sign and decimal, 0x or $ digits (parse_int_text(), c_value.cpp:1599), or a 'c' character, or for a float type a decimal number (float_from_text(), c_value.cpp:1682: its syntax is checked first, then the text is read by an istringstream imbued with the classic locale, because QApplication calls setlocale(LC_ALL, "") and a comma host would read 1.5 as 1; std::from_chars for floating point is missing from libc++ before LLVM 20, so the macOS build could not use it). nan and inf are refused. A value out of range is refused, never truncated: a person typing -1 into an unsigned long made a mistake, not a bit pattern, which is why only a script's int32 is a pattern. The 48-bit encoder rounds to nearest because the compiler does: the constants z88dk compiled into master/sccz80-floats are 0.1 = CD CC CC CC 4C 7D and 1e-10 = BE CE FE E6 5B 5F, which truncation gets wrong (CC ... and BD ...), and CVW-05 reads those bytes from the fixture at run time, never from a copy. A bitfield reads its unit's bytes, replaces its bits and writes the whole unit back (int_fits(), c_value.cpp:1700, is its range check, on the field's width).

    F1, found while planning: the reader ignored a bitfield's sign. c_format_value() and c_integer_value() returned the unsigned field for SB<s>$<w>:S, so a signed field written with -1 would have read back as 7. They now sign-extend; no committed map has a signed bitfield, so CVW-10 uses a synthetic record.

A ZRCP command table cannot gain a command (its census pins ZEsarUX's), so it is the CVAR( branch of the one assignment verb, in frame 0, with ZEsarUX's own failure text.
