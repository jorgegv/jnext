# 4.5 The documentation and CLI gates

Several documents here are **generated and committed**: the man page,
`USAGE.md`, the rendered user guide, and the rendered developer guide with its
Graphviz figures. Committed generated output is convenient — a fresh clone reads
all of it with no toolchain — and it is also a silent lie waiting to happen,
because nothing else in the build can see it no longer matches its source.

`make docs-check` closes that, as a prerequisite of **both** `make unit-test`
and `make regression`, so a stale document fails the test run itself rather than
waiting for CI or a reviewer.

## The three parts

`docs-check` runs each part as its own target and aggregates the results, so one
stale document never hides another and each prints its own remediation line:

- **`docs-man-check`** regenerates `doc/man/jnext.1` and `USAGE.md` from
  `doc/man/jnext.1.md` with pandoc and diffs them. Fix: `make docs-man`, commit.
- **`docs-userguide-check`** rebuilds the user guide from `src/doc/user-guide`
  with `mkdocs build --strict` and diffs the tree against `doc/user-guide`.
  Fix: `make docs-userguide`, commit.
- **`docs-devguide-check`** does the same for `src/doc/developer-guide` →
  `doc/developer-guide`, **and** re-renders every `diagrams/*.dot` to SVG and
  diffs those too. Checking only the site would let a hand-edited SVG through,
  since mkdocs copies it unchanged. Fix: `make docs-devguide`, commit both.

On a host without pandoc, mkdocs or graphviz the relevant part **skips**. In CI
it **hard-fails**, keyed on `$CI` — a check that skips silently reads as a pass,
which is exactly the shape being guarded against.

## The renderer fingerprint

pandoc, mkdocs-material and graphviz all emit byte-different output across
versions for identical input. A byte-diff against outputs generated by a
different toolchain therefore reports a **version gap** as staleness — which is
precisely what broke CI when it ran Ubuntu's pandoc 3.1.3 against outputs made
with 3.7.0.2, with nothing in the message hinting that the version rather than
an edit was the cause.

So each generator writes a fingerprint file next to its output recording the
tool versions that produced it, and each check compares fingerprints first. On
a mismatch it **skips the byte-diff and says so**, reporting "the guide builds
cleanly (staleness NOT compared)" rather than a false failure. CI runs in a
`fedora:44` container — the maintainer's own distro — which removes the whole
class instead of pinning tool by tool. `SOURCE_DATE_EPOCH` is pinned for the
same family of reasons: mkdocs stamps `sitemap.xml.gz` with the build date, so
an unchanged guide rendered tomorrow would otherwise differ from today's.

## What `docs-check` does NOT prove

It proves the generated outputs match `jnext.1.md`. **It proves nothing about
whether `jnext.1.md` describes the CLI that `src/main.cpp` actually parses.**

That seam was developer diligence only, and it failed twice with every gate
green: five flags entirely undocumented, and a later man page confidently
describing a wrong scale range, two GUI menus that do not exist, and a
status-bar indicator that does not exist. Both were found by reading the running
product while writing the user guide, not by any check.

## `make cli-check`

The fix was to stop treating the flag set as control flow. `src/core/cli_options.h`
holds it as a **data table** — one row per accepted spelling, with its arity, a
documentation class, and its `OptId` — and `main.cpp` dispatches from that
table, so a flag that is not in the table cannot be parsed. `cli_options_test`
then diffs the table against the OPTIONS section of `doc/man/jnext.1.md` in both
directions:

- `CLI-DOC-01` — **implemented but undocumented**: every documented-class
  spelling has a man page entry.
- `CLI-DOC-02` — **documented but unimplemented**: every man page OPTIONS entry
  is a spelling the table accepts.
- `CLI-DOC-03` — **arity disagreement**: the value arguments the parser consumes
  equal the metavars the man page shows.
- `CLI-DOC-00` guards the scrape itself, so a broken parse cannot make
  `CLI-DOC-02` vacuously true.
- `CLI-SRC-01` fails if `main.cpp`'s parse loop reintroduces a hand-rolled
  `arg == "--flag"` comparison — the pattern that made the flag set
  unenumerable, and which would re-open the gap invisibly, because such a flag
  is in neither the table nor this check.
- `CLI-BIN-01` runs the real binary end to end, proving the table drives the
  actual parser and not just this test.

The suite runs both as `make cli-check` (a prerequisite of `make regression`)
and as a declared row of `test/unit-tests.conf`. It hangs off `unit-test-build`
rather than off `docs-check`, because the table is C++ and `docs-check`
deliberately needs no compiler.

## Declaring a deliberate exception

Exceptions are declared **in the table**, never as a grep exclusion in the
checker. The documentation class `Doc::UndocumentedAlias` marks a flag that is
intentionally absent from the man page, with the reason in a comment on its row;
today that is `--sd-card`, a back-compatibility alias for `--sdcard` that exists
so older scripts keep working and should not be advertised. `CLI-DOC-05` asserts
such a flag really is absent — a deliberate exception that quietly became
documented is drift too, and would otherwise never be noticed.
`Doc::ShortAlias` covers short forms documented inline on their long form's
entry.

Adding a flag is therefore four edits: an `OptId`, a table row, a `case` in
`main.cpp` (the compiler enforces that via `-Wswitch`), and an entry in
`doc/man/jnext.1.md`. Skip the last and `cli-check` fails.

## The residual gap, stated plainly

`cli-check` covers the **flag set**, not the **prose**. The wrong scale range
and the phantom status-bar indicator were narrative text in the man page, and
nothing checks narrative text. The same is true of every page in this guide: a
stale paragraph here is the same class of defect as a stale man page, with the
difference that no gate can detect it. Keep reading the running product.
