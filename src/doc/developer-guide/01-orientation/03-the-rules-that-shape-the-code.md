# 1.3 The rules that shape the code

A handful of project-wide invariants are not visible from any single file, and
each of them exists because the failure it prevents already happened and went
unnoticed. Break one and a test run goes red for a reason that will look
unrelated to your change.

## The VHDL is the specification

The authoritative description of the hardware is the VHDL of the official
ZX Spectrum Next FPGA core — the `cores/zxnext/src/` tree of the FPGA
repository, checked out alongside this one. "Authoritative" is not a slogan;
in practice it means three things.

**Expected values come from the VHDL, never from the current code.** A test
written by reading `Layer2::render_scanline` proves only that the function
still does what it did. `doc/testing/UNIT-TEST-PLAN-EXECUTION.md` is the
process document for this and is mandatory reading before writing or
rewriting a subsystem test plan.

**Fixes are faithful, not convenient.** When a defect could be closed either
by a targeted hack or by transcribing what the VHDL does, the transcription
wins even when it is more work. The comment blocks throughout the source that
quote signal names and line numbers — `zxnext.vhd:7103`, `zxula_timing.vhd:577`
— are the record of that, and they are how the next reader checks the claim.

**Citations are machine-checked.** `doc/testing/TRACEABILITY-MATRIX.md` is
generated from those citations, and the generator validates every one against
the real FPGA source tree. See [4.4 Traceability](../04-testing/04-traceability.md).

## Some documents are generated, committed, and gated

Four outputs in the repository are produced by a tool and then committed, so a
fresh clone reads them with no toolchain installed:

| Output | Source | Regenerate with |
|---|---|---|
| `doc/man/jnext.1` and `USAGE.md` | `doc/man/jnext.1.md` | `make docs-man` |
| `doc/user-guide/` | `src/doc/user-guide/` | `make docs-userguide` |
| `doc/developer-guide/` and `src/doc/developer-guide/img/*.svg` | `src/doc/developer-guide/` and `diagrams/*.dot` | `make docs-devguide` |
| `doc/testing/TRACEABILITY-MATRIX.md` | the test sources and plan docs | regenerated by `make unit-test` |

A committed output that no longer matches its source is a silent lie no
reviewer can see, so **`make docs-check` is a prerequisite of both
`make unit-test` and `make regression`**: a stale generated document fails the
test run itself. Edit the source, re-render, and commit both halves in the
same change. On a host without pandoc, mkdocs or graphviz the relevant part
skips; in CI it hard-fails, because a check that skips silently reads as a
pass.

Know exactly what this proves. `docs-check` proves the outputs match
`jnext.1.md`. It does **not** prove `jnext.1.md` describes the CLI the program
parses — `make cli-check` does that, and only for the flag *set*: prose in the
man page's narrative sections is checked by nobody. See
[4.5 The documentation and CLI gates](../04-testing/05-documentation-and-cli-gates.md).

## The command line is data, not control flow

`src/core/cli_options.h` holds every accepted flag as a `constexpr` table of
`{ name, arity, doc-status, id }`. `src/main.cpp` dispatches from it with a
`switch` over `cli::OptId` compiled with `-Werror=switch`, so a flag added to
the table but never given a parser arm is a compile error rather than a flag
that silently does nothing. `cli_options_test` diffs the table against the
man page's OPTIONS section in both directions.

Before the table, the flag set existed only as a 47-arm `if` chain. Nothing
could enumerate it, so nothing could compare it to the documentation, and the
documentation drifted twice with every gate green. Deliberate exceptions —
there is exactly one, the undocumented `--sd-card` back-compat alias — are
declared **in the table**, never hidden in a checker's exclusion list.

## Test suites are declared, and a missing test is loud

`test/unit-tests.conf` names every unit suite together with the **exact** row
count it must report. `test/run-unit-tests.sh` refuses to run at all if that
manifest and the suites CMake registered disagree in either direction, and
fails if a suite reports any other count — including a lower one. The
regression suite has the same contract in
`test/00regression/regression_tests.conf` and `functional_tests.conf`, plus an
independent witness: every checked-in reference PNG must have a conf entry, so
truncating the file cannot silently shrink the suite.

Adding or removing a test row therefore means editing a number in a manifest.
That edit is the point: the number is the project's claim about how much it
tests, and it is made deliberately. Three suites had vanished from the counts
in a single day before this existed, each found by accident — a green result
is only as trustworthy as its denominator. [4.2 Declared suites and pinned
counts](../04-testing/02-declared-suites-and-pinned-counts.md) has the detail.

## The core does not know about the frontend

`Emulator` is constructible and runnable with no window, no audio device and
no host input, which is what makes headless testing and the unit suites
possible at all. Nothing under `src/core`, `src/cpu`, `src/memory`,
`src/video`, `src/audio`, `src/port` or `src/peripheral` includes SDL or Qt.
Where the core genuinely needs to notify a host — a joystick source changed, a
rewind restored input state — it does so through a `std::function` whose
signature carries no SDL or Qt type. Adding such an include is the one change
in this list that no gate will catch; it will simply make the core
unbuildable in some configuration months later.

Build configurations and the `ENABLE_QT_UI` / `ENABLE_DEBUGGER` arms are in
[5.2 Build configurations](../05-building/02-build-configurations.md); branch,
worktree and review discipline is in
[6.2 Branches, worktrees and review](../06-contributing/02-branches-worktrees-and-review.md).
